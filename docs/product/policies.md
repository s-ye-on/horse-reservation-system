# 운영 정책

모든 시간 계산은 `Asia/Seoul`을 기준으로 한다.

## 시간대 운영과 삭제

- `PATCH /api/admin/timeslots/{id}`는 `is_closed`를 변경해 신규 예약 가능 여부만 제어한다.
- 휴무, 우천, 시설 점검 등의 운영 마감은 `is_closed = true`, 재개는 `is_closed = false`로 처리한다.
- 마감과 재개는 기존 예약을 변경하거나 삭제하지 않는다. 기존 예약 처리는 관리자 예약 변경·취소 절차를 사용한다.
- `DELETE /api/admin/timeslots/{id}`는 잘못 생성된 시간대를 정리하는 물리 삭제다.
- 예약 또는 예약 이력이 존재하는 시간대의 삭제는 `409 Conflict`로 거부한다.
- 마감 사유 감사 요구가 생기면 현재 행의 단일 사유가 아니라 별도 상태 변경 이력으로 추가한다.
- `lessonStartAt <= now`인 지난 TimeSlot은 일반 관리자 API에서 생성, 정원 수정, 마감·재개와 삭제를 허용하지 않는다.
- 지난 TimeSlot은 기본 시간대·정원 화면에서 숨기고 과거 일정·감사·통계용 별도 조회에서만 제공한다.
- 개발 데이터나 특별 운영 데이터 정리는 일반 관리자 API가 아닌 별도 유지보수 절차로 처리한다.
- Scheduler가 시간대 상태를 갱신하지 않았더라도 각 Command는 서버 현재 시각으로 지난 시간대 여부를 검증한다.

## 예약 승인

회원이 신청한 예약은 관리자가 승인해야 확정된다. 예약 신청 직후부터 정원은 점유한다.
관리자 수동 예약은 아래 별도 정책에 따라 쿠폰 예약을 즉시 확정할 수 있다.

회원은 예약 신청일 기준 최대 3개월 이내의 수업만 예약할 수 있다. 쿠폰 예약과 1회 결제 예약에 동일하게 적용하며, `Asia/Seoul` 기준으로 `lessonDate <= today + 3 months`인 수업까지 신청할 수 있다.

### 회원 신규 예약 신청 시간

- 회원 신규 예약은 당일 수업도 신청할 수 있다.
- 신규 예약은 `Asia/Seoul` 기준 `now < lessonStartAt`일 때 허용한다.
- 정확히 수업 시작 시각부터는 `LESSON_STARTED`로 거부한다.
- 수업 전날 21:00 기준은 신규 예약 마감이 아니라 기존 예약의 변경 정책에만 적용한다.
- 조회에서 예약 가능하다고 표시했더라도 예약 Command는 트랜잭션 실행 시각으로 다시 검증한다.
- Scheduler 실행 여부나 `is_closed` 자동 변경 여부는 시간 판정의 선행 조건이 아니다.

유효한 클래스 일치 쿠폰이 있으면 `pending_admin_approval`, 없으면 `pending_payment`로 신청한다. 쿠폰 예약은 수업 시작 시각까지 승인되지 않으면 자동 만료한다. 입금대기는 신청 후 2시간과 수업 시작 중 먼저 도래한 시점에 자동 만료하고 정원을 반환한다.

### 관리자 수동 예약

- 관리자는 별도 관리자 Command로 수업 시작 전까지 특정 회원의 예약을 추가할 수 있다.
- 유효한 사용 가능 쿠폰이 있으면 관리자가 생성한 예약은 즉시 `confirmed`가 된다.
- 사용 가능 쿠폰이 없으면 `pending_payment`로 생성하며, 관리자가 입금을 확인한 뒤 `confirmed`로 전이한다.
- 입금 마감은 신청 후 2시간과 수업 시작 시각 중 먼저 도래한 시각이다.
- 관리자 수동 예약도 수업 시작, 동일 회원 중복, 정원, 클래스 자격, 시간대 마감과 쿠폰 정합성 규칙을 우회하지 않는다.
- 생성 관리자, 대상 회원과 시간대, 생성 시각, 사유, 쿠폰 또는 입금 마감 정보를 감사 이력으로 남긴다.

관리자가 예약 신청을 승인하지 않으면 `rejected`로 처리한다. 회원 또는 관리자가 접수된 예약을 이후에 취소하면 `cancelled`로 처리한다. 두 상태 모두 정원을 점유하지 않으며 운영 화면과 감사 이력에서 구분한다.

### 승인대기 경고

쿠폰 예약의 승인대기는 수업 시작 전까지 다음 기준으로 관리자에게 경고한다.

- 정상: 신청 후 2시간 이내
- 확인 필요: 신청 후 2시간 초과
- 긴급: 신청 후 24시간 초과 또는 수업 시작까지 24시간 이하

경고 기준은 운영 후 설정값으로 조정할 수 있어야 한다. 경고는 상태를 변경하거나 정원을 반환하지 않는다.

### 수업 시작 시각과 승인대기 만료

예약 생명주기의 시간 판정은 `Asia/Seoul` 기준 수업일과 시작 시각을 결합한
`lessonStartAt`을 사용한다. Scheduler 실행 여부와 관계없이 모든 예약 Command는
트랜잭션 실행 시점의 현재 시각으로 정책을 다시 검증한다.

- 수업 시작 전(`now < lessonStartAt`)에만 승인, 변경, 취소를 허용한다.
- 정확히 수업 시작 시각부터 승인, 변경, 취소를 허용하지 않는다.
- 수업 시작 시각까지 승인되지 않은 쿠폰 예약은 `approval_expired`로 만료하고 정원과
  쿠폰 임시 점유를 반환한다.
- 승인대기 만료 Job은 지연된 상태를 정리하는 수단이며 승인 API의 시간 검증을
  대체하지 않는다.
- 입금대기는 기존 2시간 마감과 수업 시작 시각 중 먼저 도래한 시점에 만료한다.
- 과거 `confirmed` 예약은 자동 완료 또는 노쇼 처리하지 않는다. 관리자가 출석 사실을
  확인하여 완료 또는 노쇼로 처리한다.
- 완료와 노쇼는 수업 시작 시각부터 허용한다. 수업 종료 시각이 모델링되기 전까지
  시작 시각을 최소 처리 경계로 사용한다.

## 관리자 예약 조회

관리자 예약 목록과 상세는 운영 판단을 위한 read-only 조회이며 조회 중 예약 상태, 정원, 쿠폰, 감사 이력을 변경하지 않는다.

- 목록 필터는 `status`, `lessonDateFrom`, `lessonDateTo`, `classType`, `keyword`를 지원한다.
- `keyword`는 회원 이름 또는 전화번호를 통합 검색한다. 전화번호는 관리자 운영 정보로 목록과 상세에 노출한다.
- 기본 정렬은 수업일 오름차순, 시작 시각 오름차순, 예약 ID 오름차순이다.
- 페이지는 0부터 시작하고 기본 크기는 20, 최대 크기는 100이다.
- 날짜 조건이 모두 없으면 오늘 이후 예약만 조회한다.
- `lessonDateFrom` 또는 `lessonDateTo` 중 하나라도 지정하면 지정된 날짜 경계만 적용하며 과거 예약도 조회할 수 있다.
- 목록과 상세에는 회원, 수업, 상태, 결제 방식, 사용 예정 또는 확정 쿠폰, 주요 상태 시각, 승인대기 경고를 제공한다.

기본 운영 목록은 오늘 이후 예약에 집중한다. 과거 예약을 중심으로 탐색하는 별도 예약 이력 화면은 후속 버전에서 검토한다.

## 목록 페이지네이션

- 관리자 예약·출석·회원·감사 이력, 회원 예약·쿠폰·쿠폰 사용 이력, 가족 그룹·구성원 목록은 Page 기반 Offset 페이지네이션을 사용한다.
- 공통 응답은 `content`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`를 제공한다.
- 기본 `page`는 0, 기본 `size`는 20이며 최대 `size`는 100이다. 최대 크기는 한 번에 반환할 응답 크기 제한이지 전체 결과 100건 제한이 아니다.
- 예정 예약은 `lessonStartAt ASC, id ASC`, 지난 예약은 `lessonStartAt DESC, id DESC`, 감사 이력과 회원 목록은 `createdAt DESC, id DESC`를 기본 정렬로 사용한다.
- 관리자 예약 기본 화면은 당일 이후 수업 운영이 목적이므로 `lessonStartAt ASC, id ASC`를 유지한다. 생성 순 탐색이 필요하면 명시적 정렬 조건으로 제공한다.
- 모든 목록은 마지막 정렬 조건에 PK를 포함해 페이지 사이의 순서를 안정적으로 유지한다.

## 외부 API 시간 계약

- 실제 하나의 시점을 나타내는 값은 RFC3339 offset을 포함해 반환한다.
- `lessonStartAt`, `paymentDueAt`, `createdAt`, `updatedAt`, `expiredAt`, `cancelledAt`, `completedAt`에는 timezone 없는 `LocalDateTime` 계약을 사용하지 않는다.
- 반복 일정의 지역 날짜·요일·시각은 `LocalDate`, `DayOfWeek`, `LocalTime`과 명시적인 `ZoneId`로 표현할 수 있다.
- 웹과 향후 Expo 앱은 기기 시간대와 관계없이 마장 시각을 `Asia/Seoul`로 표시한다.

## 관리자 감사 이력 조회

- 예약 복구, 노쇼, 일정 변경, 취소 이력은 추가 전용 `ReservationChangeLog`를 SSOT로 조회한다.
- 관리자는 `keyword`(회원 이름 또는 전화번호), `reservationId`, `occurredDateFrom`, `occurredDateTo`, `actorType`, `changeType`으로 필터링할 수 있다.
- 기간을 생략하면 전체 예약 변경 이력을 조회하며 최신 발생 시각, 이력 ID 역순으로 정렬한다.
- 페이지는 0부터 시작하고 기본 크기는 20, 최대 크기는 100이다.
- 응답은 회원·예약 식별 정보, 행위자 유형과 인증 주체, 사유 메모, 전후 상태·일정, 쿠폰 처리, 발생 시각을 제공한다.
- 조회 중 예약, 회원, 쿠폰, 감사 이력을 변경하거나 현재 상태에서 과거 이력을 추론하지 않는다.
- 쿠폰 사용 이력은 `CouponUsageLog`를 별도 SSOT로 유지하며 예약 변경 이력과 하나의 쓰기 원장으로 합치지 않는다.

## 관리자 감사 내역 다운로드

- 예약 변경 감사 이력과 쿠폰 사용 이력은 각 원장을 기준으로 별도 CSV 파일로 다운로드한다.
- 예약 감사 CSV는 감사 화면과 동일한 회원·예약·기간·행위자·변경 유형 필터와 최신순 정렬을 사용한다.
- 쿠폰 사용 CSV는 회원 이름 또는 전화번호 검색, 쿠폰 ID, 예약 ID, 발생 기간 필터를 지원하고 발생 시각과 이력 ID 역순으로 정렬한다.
- 전화번호는 검색에만 사용하며 파일에는 출력하지 않는다. JWT 인증 주체인 `actorAuthSubject`와 쿠폰 등록 관리자도 파일에 출력하지 않는다.
- 파일에는 UTF-8 BOM과 CSV quoting을 적용하고, 사용자 입력이 스프레드시트 수식으로 실행되지 않도록 보호한다.
- 다운로드는 `ROLE_ADMIN`만 허용하고 브라우저·중간 캐시에 저장하지 않도록 `Cache-Control: no-store`를 사용한다.
- 다운로드 조회는 예약, 회원, 쿠폰과 두 감사 원장의 데이터를 변경하지 않는다.

## 운영 작업 관측성

- 쿠폰 만료, 입금대기 만료와 승인대기 만료의 자동·수동 실행은 작업 이름, 실행 방식, 행위자 유형, 행위자 식별자와 결과를 구조화된 서버 로그로 남긴다.
- 자동 실행은 `SYSTEM`, 관리자 수동 실행은 인증된 JWT `sub`를 `ADMIN` 행위자로 기록한다.
- 실패 시 예외 종류와 stack trace를 기록하고 원래 예외를 다시 전파하여 기존 실패 의미를 유지한다.
- 일괄 출석의 예상 밖 항목 실패는 예약 ID, 요청 행위와 관리자 JWT `sub`를 남기되 다른 항목의 처리는 계속한다.
- 회원 이름·전화번호와 요청 본문 전체는 운영 로그에 기록하지 않는다.
- MVP-3에서는 외부 APM, 알림 전송, 영속 job 실행 원장과 자동 재시도를 도입하지 않는다.

## 회원 예약 조회

회원 예약은 `UPCOMING`과 `PAST` 표시 그룹으로 구분한다. 수업 시작 전 예약은
`UPCOMING`, 수업 시작 시각부터는 상태와 관계없이 `PAST`로 분류한다. 예정 예약은
수업일, 시작 시각, 예약 ID 오름차순으로 제공하고 지난 예약은 수업일, 시작 시각,
예약 ID 내림차순으로 제공한다.

조회 응답은 변경, 취소, 완료, 노쇼와 필요한 관리자 조회의 승인 행동마다 독립적인
`allowed`와 `blockedReason`을 제공한다. 이 값은 화면 표시를 위한 Read Model이며 실제
Command는 트랜잭션 실행 시점에 같은 정책을 다시 검증한다. 프론트엔드는 예약 상태와
기기 시각으로 행동 가능 여부를 재구현하지 않는다.

회원에게 반려 사유와 최종 쿠폰 처리 결과를 제공한다. 내부 운영 정보인 관리자 메모, 처리 관리자 식별자, 취소 책임 분류는 노출하지 않는다.

## 쿠폰 임시 점유

예약 신청 시 쿠폰을 차감하지 않지만, 선택된 쿠폰의 사용 가능 횟수 1회를 임시 점유한다. 따라서 잔여 1회인 쿠폰으로 여러 승인대기 예약을 만들 수 없다.

- 신청: 만료일이 가장 가까운 유효 쿠폰에서 1회 임시 점유
- 관리자 승인: 임시 점유를 확정 예약 점유로 전환
- 반려 또는 마감 전 취소: 임시 점유 해제
- 수업 완료: 실제 1회 차감
- 노쇼·마감 후 취소: 관리자 결정에 따라 차감 또는 반환

쿠폰 예약은 `coupon_action`으로 `DEDUCT` 또는 `RETURN`만 허용한다. 이미 존재하는 임시 점유를 반드시 차감 또는 반환으로 종결해야 하므로 `NONE`은 허용하지 않는다.

1회 결제 예약은 `coupon_action`으로 `NONE`만 허용한다. 쿠폰이 존재하지 않으므로 `DEDUCT`와 `RETURN`은 허용하지 않는다.

회원에게 선택된 쿠폰, 만료일, 현재 잔여 횟수와 점유 후 사용 가능 횟수를 보여준다.

## 동일 회원의 동일 시간대 중복 예약

- 하나의 회원 계정은 한 명의 실제 기승자를 나타내며 다른 가족 구성원을 대신 예약하지 않는다.
- 동일 회원은 같은 `lessonDate`와 `startTime`에 활성 예약을 두 개 이상 가질 수 없다.
- 활성 예약은 `pending_admin_approval`, `pending_payment`, `confirmed`다.
- 현재 `TimeSlot`은 `lessonDate`와 `startTime`으로 식별되는 비중첩 고정 수업 시간대이며 수업 종료 시각을 저장하지 않는다.
- 따라서 MVP-3.1의 중복 판정은 동일 `lessonDate/startTime` 기준이다. 향후 수업 시간 구간이 겹칠 수 있는 모델을 도입하면 구간 중복 정책과 DB 제약을 별도로 재설계한다.
- Application 선검사와 MySQL 제약을 함께 사용하여 동시 요청에서도 불변식을 지킨다.

## 예약 생성 요청 멱등성

- 회원 예약 생성과 관리자 수동 예약 생성은 Horse API 계약의 `Idempotency-Key` 요청 헤더를 사용한다.
- 키 범위는 인증 주체와 API 작업 단위이며 회원 생성과 관리자 수동 생성은 서로 다른 범위다.
- 같은 키와 같은 요청 본문은 최초 성공 결과를 반환하고, 같은 키에 다른 본문을 사용하면 `409 Conflict`로 거부한다.
- 요청 fingerprint와 최초 성공 결과를 저장하며 실패 결과는 저장하지 않는다.
- 예약 생성, 쿠폰 점유와 멱등성 완료 기록은 하나의 DB 트랜잭션으로 원자적으로 커밋한다.
- 비즈니스 변경 커밋과 멱등성 완료 기록 사이에 분리된 커밋 구간을 두지 않는다.
- 멱등성 기록의 기본 보관 기간은 24시간이며 정리 Job은 보관 데이터만 정리하고 API 판정을 대신하지 않는다.

## 쿠폰

- 종류는 일반, 마장마술, 장애물 10회권이다.
- 동일 종류의 쿠폰을 여러 장 보유할 수 있다.
- 예약 클래스와 쿠폰 종류가 일치해야 한다.
- 여러 쿠폰이 유효하면 이미 사용 중이라 만료일이 있는 쿠폰을 미사용 쿠폰보다 먼저 선택한다.
- 자동 선택 순서는 만료일이 빠른 순, 등록일이 오래된 순, 쿠폰 ID가 작은 순이다. 등록일과 ID는 결정적인 결과를 위한 tie-breaker다.
- 미사용 쿠폰은 기존 사용 중 쿠폰을 모두 사용한 후 FIFO로 선택한다.
- 첫 번째 쿠폰 수업이 `completed`가 된 수업일을 첫 기승일로 정한다.
- 첫 기승일부터 3개월 동안 유효하다.
- 수업일이 만료일 이후면 예약할 수 없다.
- 예약 당시 정상적으로 쿠폰 1회가 임시 점유된 기존 예약은 이후 첫 사용으로 계산된 만료일을 초과하더라도 유지하며 완료 시 차감한다. 이는 데이터 이관, 관리자 예외, 정책 변경 상황에서 일관성을 유지하기 위한 방어 규칙이다.
- 만료일 계산 이후 생성하는 신규 예약이나 예약 변경은 계산된 만료일 이후 수업을 선택할 수 없다.
- 만료된 잔여 횟수는 소멸하며 차감 대상으로 사용하지 않는다.
- 쿠폰마다 무료 변경권 1회를 가진다.
- 1회 결제 예약은 쿠폰을 생성하거나 차감하지 않는다.

## 가족 그룹과 쿠폰 공유

- 가족 그룹은 관리자만 생성, 구성원 추가·제거, 해제할 수 있다.
- 회원은 동시에 하나의 활성 가족 그룹에만 속할 수 있다.
- Coupon 레코드와 원소유자는 유지하며 가족 쿠폰 하나로 합치지 않는다.
- 활성 가족 구성원은 그룹 구성원이 소유한 모든 유효 쿠폰을 공동으로 사용할 수 있고, 그룹 등록 전 발급 쿠폰도 포함한다.
- 가족 등록과 제거는 신규 쿠폰 선택 권한만 변경한다. 기존 예약과 점유는 유지하며 취소 시 원래 Coupon으로 반환한다.
- 가족 전체 후보는 만료일이 있는 쿠폰을 먼저 선택하고 `expires_at ASC`, `created_at ASC`, `coupon_id ASC` 순으로 결정한다.
- 만료일이 없는 쿠폰은 MySQL 기본 NULL 정렬에 의존하지 않고 명시적으로 마지막에 배치한다.
- 사용 이력에는 예약 회원, 쿠폰 원소유자, 실제 Coupon, 사용 당시 가족 그룹, 예약, 처리 유형, 처리 주체와 시각을 남긴다.
- 가족 그룹 변경은 관리자, 처리 시각과 필수 사유를 추가 전용 감사 이력으로 남긴다.

## 클래스와 탑승 이력

일반 기승 완료 횟수만 일반 클래스 등급에 반영한다. 마장마술과 장애물 완료 횟수는 별도 이력으로 집계한다.

- `calculatedClass`는 일반 기승 완료 횟수로 계산한다.
- 관리자는 자동 계산보다 높거나 낮은 `manualClassOverride`를 지정하고 해제할 수 있다.
- `effectiveClass`는 수동 지정이 있으면 수동 값, 없으면 자동 계산값이다.
- 클래스 수동 지정·해제는 변경 전후 값, 관리자, 시각과 필수 사유를 감사 이력으로 남긴다.
- 과거 기승 횟수 보정은 클래스 수동 지정과 별도 기능이며 기존 값을 무감사 덮어쓰지 않고 조정 원장으로 기록한다.

## 타임별 일괄 출석 처리

- 관리자는 같은 수업 날짜와 시작 시각의 예약을 최대 8건까지 한 요청으로 처리한다.
- 각 예약의 처리 유형은 출석 완료(`complete`) 또는 노쇼(`no_show`)다.
- 출석 완료는 기존 단건 완료 정책을 적용하고, 노쇼는 예약 유형에 맞는 `coupon_action`과 최대 500자의 필수 관리자 메모를 적용한다.
- 요청한 날짜·시각과 현재 예약 일정이 다르면 해당 예약만 실패한다.
- 각 예약은 독립 트랜잭션으로 처리한다. 한 예약의 실패는 다른 예약의 성공을 롤백하지 않는다.
- 구조적으로 유효한 요청은 항목별 성공·실패, 최종 상태 또는 오류 정보를 반환한다.
- 반복 요청은 기존 완료·노쇼 멱등성에 따라 쿠폰, 기승 횟수, 노쇼 이력을 중복 반영하지 않는다.

## 예약 변경

변경 마감은 수업 전날 21:00이다.

마감 전은 `Asia/Seoul` 기준 현재 시각이 수업 전날 21:00보다 이른 경우다. 정확히 21:00부터는 마감 후로 판정하며, 평일·주말은 수업일의 요일을 기준으로 구분한다.

- 마감 전: 날짜와 시간 변경 가능, 쿠폰 차감 및 무료 변경권 사용 없음
- 마감 후 무료 변경권 보유: 날짜와 시간 변경 가능, 무료 변경권 사용
- 마감 후 무료 변경권 미보유: 평일에 한해 같은 날의 다른 시간으로만 변경 가능
- 평일 당일 내 시간 변경: 무료 변경권을 사용하지 않음
- 주말 당일 변경: 불가

변경 대상 시간대의 정원을 다시 검증하고 성공 시 기존 정원을 해제한다.

변경은 기존 Reservation의 날짜와 시간만 바꾸며 예약 상태, 결제 방식, 연결 쿠폰, 승인 신청 시각, 입금 마감 시각을 유지한다. 따라서 입금대기 2시간과 승인대기 경고는 최초 예약 신청 시각을 기준으로 계속 계산한다. 관리자 변경도 같은 변경 가능 정책을 적용하고 관리자 메모를 필수로 기록한다.

## 예약 취소

- 마감 전: 쿠폰 점유 반환 또는 1회 결제 취소
- 마감 후 회원 사유: 기본 차감
- 마장 사유: 반환
- 노쇼: 기본 차감
- 관리자 처리: 예약 유형별 허용 범위 안에서 쿠폰 처리를 직접 선택하고 사유 메모 필수

관리자 취소 preview는 선택한 책임에 따른 기본 쿠폰 처리를 권고한다. 마장 책임(`stable`)과 운영 예외(`exception`)의 쿠폰 예약은 `return`, 회원 책임(`member`)의 쿠폰 예약은 마감 전 `return`·마감 후 `deduct`를 권고한다. 관리자는 실행 시 예약 유형별 허용 범위 안에서 권고와 다른 최종 처리를 선택할 수 있다.

회원 질병처럼 회원 사유지만 마장이 예외를 허용할 수 있으므로 최종 쿠폰 처리는 관리자가 결정한다.

회원이 직접 취소하면 활성 예약은 즉시 `cancelled`로 전이한다. 회원 직접 취소의 책임은 `member`로 기록하며 쿠폰 예약은 마감 전 `return`, 마감 후 `deduct`, 1회 결제 예약은 항상 `none`을 적용한다. 예외 반환이 필요한 회원은 관리자가 취소 처리하도록 요청한다.

회원 취소 화면은 실행 전에 서버의 취소 preview를 조회해 예상 쿠폰 처리를 표시한다. preview와 실제 취소는 동일한 정책 판정기를 사용하며, 실행 시점의 판정이 최종 결과다.

## 입금대기

- 유효한 클래스 일치 쿠폰이 없을 때 1회 결제 입금대기로 신청한다.
- 신청 후 2시간과 수업 시작 중 먼저 도래한 시점까지 정원을 점유한다.
- 만료 경계 전에 관리자가 입금을 확인하면 예약을 확정한다.
- 먼저 도래한 만료 경계에 도달하면 `payment_expired`로 바꾸고 정원을 반환한다.
- 회원에게 만료 후 관리자에게 연락하라는 안내를 표시한다.
- 관리자는 만료 예약을 복구할 수 있지만 현재 정원이 남아 있을 때만 가능하다.
- 자동 만료는 Spring Scheduler가 애플리케이션 Service를 직접 호출해 실행한다.
- 관리자는 운영상 필요할 때 `POST /api/admin/jobs/expire-pending-payments`로 동일한 만료 작업을 수동 실행할 수 있다.
- 자동 실행과 수동 실행은 같은 트랜잭션·잠금·멱등성 규칙을 사용한다.
- `payment_expired`는 운영 자동화 상태이며 최종 결제 실패 판정이 아니다. 늦은 입금 확인 시 관리자는 정원을 재확보할 수 있는 경우 예약을 복구한다.
- M1에서는 시스템 역할을 추가하지 않으며 관리자 수동 실행은 `ROLE_ADMIN`으로 제한한다.
