# 운영 정책

모든 시간 계산은 `Asia/Seoul`을 기준으로 한다.

## 시간대 운영과 삭제

- `PATCH /api/admin/timeslots/{id}`는 호환 진입점이며 개별 휴강 시작·철회·재개 workflow에 위임한다. `is_closed` 또는 `admin_closed`를 직접 변경하지 않는다.
- 개별 수업의 휴강, 우천, 시설 점검 등의 운영 마감은 `TimeSlotClosure` 작업으로 관리하고 `admin_closed = true`를 적용한다.
- 휴강 시작은 기존 예약을 자동 취소하지 않는다. 시작 시점의 활성 예약을 고정 영향 목록으로 보존하고 휴강 전용 취소 절차로 한 건씩 정리한다.
- `DELETE /api/admin/timeslots/{id}`는 잘못 생성된 시간대를 정리하는 물리 삭제다.
- 예약 또는 예약 이력이 존재하는 시간대의 삭제는 `409 Conflict`로 거부한다.
- 자동 생성된 TimeSlot은 동기화에서 물리 삭제하지 않는다. 운영 제외가 필요하면 행을 유지한 채 닫아 재생성을 막는다.
- TimeSlot의 현재 마감 원인과 변경 이력은 각각 현재 행과 추가 전용 `ScheduleAuditLog`로 구분한다.
- `lessonStartAt <= now`인 지난 TimeSlot은 일반 관리자 API에서 생성, 정원 수정, 마감·재개와 삭제를 허용하지 않는다.
- 지난 TimeSlot은 기본 시간대·정원 화면에서 숨기고 과거 일정·감사·통계용 별도 조회에서만 제공한다.
- 개발 데이터나 특별 운영 데이터 정리는 일반 관리자 API가 아닌 별도 유지보수 절차로 처리한다.
- Scheduler가 시간대 상태를 갱신하지 않았더라도 각 Command는 서버 현재 시각으로 지난 시간대 여부를 검증한다.

## 정규 시간표와 운영일

- 정규 수업 시작 시각은 `09:00`, `10:00`, `11:00`, `13:30`, `14:30`, `15:30`, `16:30`이다.
- 정규 및 관리자 수동 TimeSlot은 모두 45분이며 같은 날짜 안에서 종료되어야 한다.
- 정규 시간표 Template은 요일, 시작·종료 시각, `totalCapacity`, `roundArenaCapacity`, `classCapacities`를 직접 보유한다. 별도 CapacityProfile은 사용하지 않는다.
- 정규 시간표 Template과 정기 휴일은 독립적으로 관리한다. 기본 정기 휴일인 월요일에도 `OPEN` 시 적용할 정규 Template이 존재해야 한다.
- 정기 휴일은 휴무 요일, 적용 시작일, 선택적 종료일, 사유, 활성 여부와 변경 관리자를 보존한다.
- 날짜별 운영 상태는 실제 `ScheduleDate` 행으로 관리하며 `NORMAL`, `OPEN`, `CLOSING`, `CLOSED`를 사용한다.
- `ScheduleDate`는 `Asia/Seoul` 기준 오늘부터 `today.plusMonths(3)`까지 양 끝 날짜를 포함해 미리 생성한다. Scheduler는 매일 새 범위 끝 날짜를 보충한다.
- 행이 없음을 `NORMAL`로 해석하지 않는다. 예약·변경·관리자 수동 예약·휴무 전환처럼 정합성이 필요한 Command는 같은 `ScheduleDate` 행을 잠그고 상태를 재검증한다.
- 과거 `ScheduleDate`는 현재 범위에서 삭제하지 않는다. 보존 기간은 예약·TimeSlot·감사 이력의 전체 보존 정책이 정해진 뒤 별도 Task에서 결정한다.
- 정규 TimeSlot 동기화 범위는 오늘부터 `today.plusMonths(3)`까지이며 누락 occurrence만 보충한다. 반복 또는 동시 실행에도 같은 `lessonDate/startTime` 행을 중복 생성하지 않는다.
- Template 정원은 새 `TEMPLATE` occurrence를 생성할 때만 기본값으로 복사한다.
- 관리자가 개별 TimeSlot에 적용한 정원 보정은 자동 동기화가 덮어쓰지 않는다.
- Template 변경을 기존 미래 TimeSlot에 반영하려면 영향 미리보기 후 명시적 동기화 Command를 실행해야 한다.
- 자동 동기화는 활성 예약 수보다 작게 TimeSlot 정원을 축소하지 않는다.
- Template 또는 정기 휴일 변경은 일정 설정 version을 `SYNCING`으로 전환한 뒤 날짜별 occurrence에 반영한다. 전체 범위가 같은 version으로 동기화될 때까지 신규 예약, 해당 날짜로의 예약 변경·복구, 관리자 수동 예약과 수동 TimeSlot 생성을 허용하지 않는다.
- `SYNCING` 중 회원 예약 가능 TimeSlot 조회도 일시 차단한다. 기존 예약·쿠폰·휴무 정리 조회, 휴무 정리 취소, 반려, 자동 입금·승인 만료, 동기화 상태 조회와 동일 version 재시도는 계속 허용한다.
- `SYNCING` 차단은 `SCHEDULE_CONFIG_SYNC_IN_PROGRESS`와 `503 Service Unavailable`을 반환한다. 안정적인 예상 완료 시간을 계산할 수 있을 때만 `Retry-After`를 제공한다.
- 미완료 `SYNCING`은 서버 재시작 또는 복구 Scheduler에서 같은 pending version으로 재개한다. 모든 대상 날짜의 적용 version이 일치하기 전에는 오래됐다는 이유로 강제 `ACTIVE` 전환하지 않는다.
- 같은 요일에 적용 기간이 겹치는 활성 정기 휴일 규칙은 허용하지 않는다. 동시에 등록해도 하나만 성공해야 한다.
- 날짜 `OPEN`은 정기 휴일을 우회하여 해당 요일의 정규 Template 전체를 생성한다. 일부 수업만 운영하려면 관리자가 수동 TimeSlot을 추가한다.
- 정기 휴일에도 수동 TimeSlot 추가는 허용하지만, 날짜가 `CLOSING` 또는 `CLOSED`이면 수동 추가도 금지한다.
- 운영 우선순위는 날짜 `CLOSING/CLOSED`, 개별 TimeSlot 마감, 날짜 `OPEN`, 정기 휴일, 정규 Template 순이다.
- 개별 TimeSlot의 관리자 휴강, 정기 휴일, Template 비활성화 원인은 독립적으로 보존한다. 하나의 원인이 해제되어도 다른 원인이 남아 있으면 TimeSlot을 재개하지 않는다.
- 정기 휴일과 Template 비활성화는 자동 생성된 `TEMPLATE` TimeSlot에만 적용한다. `MANUAL` TimeSlot은 날짜 휴무 또는 관리자 휴강이 아닌 설정 동기화로 닫지 않는다.
- 설정 변경으로 TEMPLATE TimeSlot이 닫혀도 기존 활성 예약은 자동 취소하지 않는다. 설정 version 동기화가 끝나면 `ACTIVE`로 복귀하고 남은 예약은 별도 휴무 정리 목록과 진행 상태로 관리한다.
- 날짜 전체 휴무는 미래 날짜만 허용한다. 당일 일부 또는 전체 휴장은 개별 TimeSlot 휴강 절차를 사용한다.

### 날짜 전체 휴무

- 활성 예약이 없으면 미래 `ScheduleDate`를 즉시 `CLOSED`로 확정할 수 있다.
- 활성 예약이 있으면 먼저 `CLOSING`으로 전환하여 회원 신규 예약, 해당 날짜로의 예약 변경, 관리자 수동 예약, 수동 TimeSlot 추가와 자동 생성을 차단한다.
- 활성 예약은 `pending_admin_approval`, `pending_payment`, `confirmed`다.
- 영향 예약은 자동 일괄 취소하지 않는다. 관리자는 영향 건수·대상 목록·진행률을 확인하고 휴무 정리 전용 취소 Command로 한 건씩 정리한다.
- 휴무 정리 취소는 `stable` 책임을 강제한다. 쿠폰 예약은 `RETURN`, 1회 결제 예약은 기존 쿠폰 정책에 따라 `NONE`을 적용한다.
- 활성 예약이 0건일 때만 같은 트랜잭션에서 다시 확인한 뒤 `CLOSED`로 확정한다. 남아 있으면 `TIMESLOT_ACTIVE_RESERVATIONS_EXIST_ON_CLOSURE_DATE`와 `409 Conflict`를 반환한다.
- `CLOSING` 중 회원 직접 취소는 허용하지 않는다.
- `CLOSING` 중 예약 승인, 입금 확인, 입금 만료 복구와 해당 날짜로의 예약 변경은 허용하지 않는다.
- `CLOSING` 중 예약 반려, 자동 입금 만료, 자동 승인 만료와 휴무 정리 전용 관리자 취소는 허용한다.
- `CLOSING` 취소 시 직전의 `NORMAL` 또는 `OPEN` 상태로 돌아가지만 이미 취소된 예약은 자동 복구하지 않는다.
- 회원 알림과 일괄 취소는 현재 범위에서 제외한다.

### 개별 TimeSlot 휴강

- 개별 휴강 시작은 `ScheduleDate`와 대상 TimeSlot을 잠그고 `admin_closed = true`를 적용한 뒤 시작 시점의 활성 예약 ID를 고정 영향 목록으로 저장한다. 기존 예약은 자동 취소하지 않는다.
- 휴강 작업은 `IN_PROGRESS`, `COMPLETED`, `WITHDRAWN` 상태를 사용한다. 동일 TimeSlot에는 최대 하나의 `IN_PROGRESS` 작업만 존재한다.
- 고정 영향 목록의 membership은 변경하지 않는다. 영향 예약이 비활성 상태가 되거나 원래 TimeSlot에서 다른 TimeSlot으로 이동하면 해결된 것으로 계산한다.
- 휴강 완료는 고정 영향 예약이 모두 해결되고 대상 TimeSlot의 현재 활성 예약이 0건일 때만 허용한다. 완료 직전에 두 조건을 잠금 안에서 다시 검사한다.
- 휴강 중에는 회원·관리자 신규 예약, 해당 TimeSlot으로의 변경, 승인, 입금 확인·복구, 일반 관리자 취소·일반 변경, 완료와 노쇼를 차단한다.
- 휴강 전용 관리자 취소, 휴강을 인식하는 회원 직접 취소, 반려, 자동 입금 만료와 자동 승인 만료는 허용한다.
- 휴강 전용 취소와 휴강 중 회원 직접 취소는 마장 책임을 적용한다. 쿠폰 예약은 `stable/RETURN`, 1회 결제 예약은 `stable/NONE`으로 처리한다.
- `IN_PROGRESS` 휴강은 시작 이후 해결된 고정 영향 예약이 0건일 때만 철회할 수 있다. 철회는 `admin_closed = false`만 적용하며 이미 처리된 예약을 복구하지 않는다.
- `COMPLETED` 휴강은 수업 시작 전이고 날짜 상태가 허용할 때만 명시적으로 재개할 수 있다. 재개는 `admin_closed = false`만 적용하며 다른 마감 원인과 날짜 `CLOSING/CLOSED`를 우회하지 않는다.
- 휴강을 철회하거나 재개해도 취소되거나 이동된 기존 예약은 자동 복구하지 않는다.
- 휴강 시작·완료·철회·재개와 실제 예약 정리는 각각 append-only 감사 로그로 남긴다.
- 지난 TimeSlot은 휴강·재개할 수 없다. 당일 휴강은 아직 시작하지 않은 TimeSlot만 허용한다.
- 연락 여부·메모·담당자는 휴강 해결 상태와 분리하며 현재 범위에서는 저장하지 않는다.

## 예약 승인

회원이 신청한 예약은 관리자가 승인해야 확정된다. 예약 신청 직후부터 정원은 점유한다.
관리자 수동 예약은 아래 별도 정책에 따라 쿠폰 예약을 즉시 확정할 수 있다.

회원은 예약 신청일 기준 최대 3개월 이내의 수업만 예약할 수 있다. 쿠폰 예약과 1회 결제 예약에 동일하게 적용하며, `Asia/Seoul` 기준으로 `lessonDate <= today + 3 months`인 수업까지 신청할 수 있다.

### 회원 신규 예약 신청 시간

- 회원 신규 예약은 당일 수업도 신청할 수 있다.
- 회원 예약 마감은 `bookingDeadlineAt = lessonStartAt - 3시간`이다.
- `Asia/Seoul` 기준 `now <= bookingDeadlineAt`이면 신청할 수 있고, 그 이후에는 `RESERVATION_BOOKING_DEADLINE_PASSED`로 거부한다.
- 정확히 수업 시작 시각부터는 `RESERVATION_LESSON_ALREADY_STARTED`로 거부한다.
- 회원 예약 가능 조회에서도 마감된 TimeSlot은 노출하지 않는다.
- 수업 전날 21:00 기준은 신규 예약 마감이 아니라 기존 예약의 변경 정책에만 적용한다.
- 조회에서 예약 가능하다고 표시했더라도 예약 Command는 트랜잭션 실행 시각으로 다시 검증한다.
- Scheduler 실행 여부나 `is_closed` 자동 변경 여부는 시간 판정의 선행 조건이 아니다.

유효한 클래스 일치 쿠폰이 있으면 `pending_admin_approval`, 없으면 `pending_payment`로 신청한다. 쿠폰 예약은 수업 시작 시각까지 승인되지 않으면 자동 만료한다. 입금대기는 신청 후 2시간과 수업 시작 중 먼저 도래한 시점에 자동 만료하고 정원을 반환한다.

### 관리자 수동 예약

- 관리자는 별도 관리자 Command로 수업 시작 전까지 특정 회원의 예약을 추가할 수 있다.
- 관리자는 회원의 3시간 신규 예약 마감을 우회하지만 `now >= lessonStartAt`이면 예약할 수 없다.
- 유효한 사용 가능 쿠폰이 있으면 관리자가 생성한 예약은 즉시 `confirmed`가 된다.
- 사용 가능 쿠폰이 없으면 `pending_payment`로 생성하며, 관리자가 입금을 확인한 뒤 `confirmed`로 전이한다.
- 입금 마감은 신청 후 2시간과 수업 시작 시각 중 먼저 도래한 시각이다.
- 관리자 수동 예약도 수업 시작, 동일 회원 중복, 정원, 클래스 자격, 시간대 마감과 쿠폰 정합성 규칙을 우회하지 않는다.
- 생성 관리자, 대상 회원과 시간대, 생성 시각, 사유, 쿠폰 또는 입금 마감 정보를 감사 이력으로 남긴다.

관리자가 예약 신청을 승인하지 않으면 `rejected`로 처리한다. 회원 또는 관리자가 접수된 예약을 이후에 취소하면 `cancelled`로 처리한다. 두 상태 모두 정원을 점유하지 않으며 운영 화면과 감사 이력에서 구분한다.

### 승인대기 경고

쿠폰 예약의 승인대기는 수업 시작 전까지 다음 기준으로 관리자에게 경고한다.

- 정상: 신청 후 2시간 이내
- 확인 필요: 신청 후 2시간 초과
- 긴급: 신청 후 24시간 초과 또는 수업 시작까지 24시간 이하

경고 기준은 운영 후 설정값으로 조정할 수 있어야 한다. 경고는 상태를 변경하거나 정원을 반환하지 않는다.

### 수업 시작 시각과 승인대기 만료

예약 생명주기의 시간 판정은 `Asia/Seoul` 기준 수업일과 시작 시각을 결합한
`lessonStartAt`을 사용한다. Scheduler 실행 여부와 관계없이 모든 예약 Command는
트랜잭션 실행 시점의 현재 시각으로 정책을 다시 검증한다.

- 수업 시작 전(`now < lessonStartAt`)에만 승인, 변경, 취소를 허용한다.
- 정확히 수업 시작 시각부터 승인, 변경, 취소를 허용하지 않는다.
- 수업 시작 시각까지 승인되지 않은 쿠폰 예약은 `approval_expired`로 만료하고 정원과
  쿠폰 임시 점유를 반환한다.
- 승인대기 만료 Job은 지연된 상태를 정리하는 수단이며 승인 API의 시간 검증을
  대체하지 않는다.
- 입금대기는 기존 2시간 마감과 수업 시작 시각 중 먼저 도래한 시점에 만료한다.
- 과거 `confirmed` 예약은 자동 완료 또는 노쇼 처리하지 않는다. 관리자가 출석 사실을
  확인하여 완료 또는 노쇼로 처리한다.
- 완료와 노쇼는 수업 시작 시각부터 허용한다. 수업 종료 시각이 모델링되기 전까지
  시작 시각을 최소 처리 경계로 사용한다.

## 관리자 예약 조회

관리자 예약 목록과 상세는 운영 판단을 위한 read-only 조회이며 조회 중 예약 상태, 정원, 쿠폰, 감사 이력을 변경하지 않는다.

- 목록 필터는 `status`, `lessonDateFrom`, `lessonDateTo`, `classType`, `keyword`를 지원한다.
- `keyword`는 회원 이름 또는 전화번호를 통합 검색한다. 전화번호는 관리자 운영 정보로 목록과 상세에 노출한다.
- 기본 정렬은 수업일 오름차순, 시작 시각 오름차순, 예약 ID 오름차순이다.
- 페이지는 0부터 시작하고 기본 크기는 20, 최대 크기는 100이다.
- 날짜 조건이 모두 없으면 오늘 이후 예약만 조회한다.
- `lessonDateFrom` 또는 `lessonDateTo` 중 하나라도 지정하면 지정된 날짜 경계만 적용하며 과거 예약도 조회할 수 있다.
- 목록과 상세에는 회원, 수업, 상태, 결제 방식, 사용 예정 또는 확정 쿠폰, 주요 상태 시각, 승인대기 경고를 제공한다.

기본 운영 목록은 오늘 이후 예약에 집중한다. 과거 예약을 중심으로 탐색하는 별도 예약 이력 화면은 후속 버전에서 검토한다.

## 목록 페이지네이션

- 관리자 예약·출석·회원·감사 이력, 회원 예약·쿠폰·쿠폰 사용 이력, 가족 그룹·구성원 목록은 Page 기반 Offset 페이지네이션을 사용한다.
- 공통 응답은 `content`, `page`, `size`, `totalElements`, `totalPages`, `hasNext`를 제공한다.
- 기본 `page`는 0, 기본 `size`는 20이며 최대 `size`는 100이다. 최대 크기는 한 번에 반환할 응답 크기 제한이지 전체 결과 100건 제한이 아니다.
- 예정 예약은 `lessonStartAt ASC, id ASC`, 지난 예약은 `lessonStartAt DESC, id DESC`, 감사 이력과 회원 목록은 `createdAt DESC, id DESC`를 기본 정렬로 사용한다.
- 관리자 예약 기본 화면은 당일 이후 수업 운영이 목적이므로 `lessonStartAt ASC, id ASC`를 유지한다. 생성 순 탐색이 필요하면 명시적 정렬 조건으로 제공한다.
- 모든 목록은 마지막 정렬 조건에 PK를 포함해 페이지 사이의 순서를 안정적으로 유지한다.

## 외부 API 시간 계약

- 실제 하나의 시점을 나타내는 값은 RFC3339 offset을 포함해 반환한다.
- `lessonStartAt`, `paymentDueAt`, `createdAt`, `updatedAt`, `expiredAt`, `cancelledAt`, `completedAt`에는 timezone 없는 `LocalDateTime` 계약을 사용하지 않는다.
- 반복 일정의 지역 날짜·요일·시각은 `LocalDate`, `DayOfWeek`, `LocalTime`과 명시적인 `ZoneId`로 표현할 수 있다.
- 웹과 향후 Expo 앱은 기기 시간대와 관계없이 마장 시각을 `Asia/Seoul`로 표시한다.

## 관리자 감사 이력 조회

- 예약 복구, 노쇼, 일정 변경, 취소 이력은 추가 전용 `ReservationChangeLog`를 SSOT로 조회한다.
- 관리자는 `keyword`(회원 이름 또는 전화번호), `reservationId`, `occurredDateFrom`, `occurredDateTo`, `actorType`, `changeType`으로 필터링할 수 있다.
- 기간을 생략하면 전체 예약 변경 이력을 조회하며 최신 발생 시각, 이력 ID 역순으로 정렬한다.
- 페이지는 0부터 시작하고 기본 크기는 20, 최대 크기는 100이다.
- 응답은 회원·예약 식별 정보, 행위자 유형과 인증 주체, 사유 메모, 전후 상태·일정, 쿠폰 처리, 발생 시각을 제공한다.
- 조회 중 예약, 회원, 쿠폰, 감사 이력을 변경하거나 현재 상태에서 과거 이력을 추론하지 않는다.
- 쿠폰 사용 이력은 `CouponUsageLog`를 별도 SSOT로 유지하며 예약 변경 이력과 하나의 쓰기 원장으로 합치지 않는다.

## 관리자 감사 내역 다운로드

- 예약 변경 감사 이력과 쿠폰 사용 이력은 각 원장을 기준으로 별도 CSV 파일로 다운로드한다.
- 예약 감사 CSV는 감사 화면과 동일한 회원·예약·기간·행위자·변경 유형 필터와 최신순 정렬을 사용한다.
- 쿠폰 사용 CSV는 회원 이름 또는 전화번호 검색, 쿠폰 ID, 예약 ID, 발생 기간 필터를 지원하고 발생 시각과 이력 ID 역순으로 정렬한다.
- 전화번호는 검색에만 사용하며 파일에는 출력하지 않는다. JWT 인증 주체인 `actorAuthSubject`와 쿠폰 등록 관리자도 파일에 출력하지 않는다.
- 파일에는 UTF-8 BOM과 CSV quoting을 적용하고, 사용자 입력이 스프레드시트 수식으로 실행되지 않도록 보호한다.
- 다운로드는 `ROLE_ADMIN`만 허용하고 브라우저·중간 캐시에 저장하지 않도록 `Cache-Control: no-store`를 사용한다.
- 다운로드 조회는 예약, 회원, 쿠폰과 두 감사 원장의 데이터를 변경하지 않는다.

## 운영 작업 관측성

- 쿠폰 만료, 입금대기 만료와 승인대기 만료의 자동·수동 실행은 작업 이름, 실행 방식, 행위자 유형, 행위자 식별자와 결과를 구조화된 서버 로그로 남긴다.
- 자동 실행은 `SYSTEM`, 관리자 수동 실행은 인증된 JWT `sub`를 `ADMIN` 행위자로 기록한다.
- 실패 시 예외 종류와 stack trace를 기록하고 원래 예외를 다시 전파하여 기존 실패 의미를 유지한다.
- 일괄 출석의 예상 밖 항목 실패는 예약 ID, 요청 행위와 관리자 JWT `sub`를 남기되 다른 항목의 처리는 계속한다.
- 회원 이름·전화번호와 요청 본문 전체는 운영 로그에 기록하지 않는다.
- MVP-3에서는 외부 APM, 알림 전송, 영속 job 실행 원장과 자동 재시도를 도입하지 않는다.

## 회원 예약 조회

회원 예약은 `UPCOMING`과 `PAST` 표시 그룹으로 구분한다. 수업 시작 전 예약은
`UPCOMING`, 수업 시작 시각부터는 상태와 관계없이 `PAST`로 분류한다. 예정 예약은
수업일, 시작 시각, 예약 ID 오름차순으로 제공하고 지난 예약은 수업일, 시작 시각,
예약 ID 내림차순으로 제공한다.

회원 예약 목록은 선택적으로 표시 그룹과 예약 상태를 서버에서 필터링한다. 필터가
지정되면 필터가 적용된 전체 결과를 기준으로 Page의 `totalElements`, `totalPages`,
`hasNext`를 계산한다. 표시 그룹을 생략하면 예정 예약을 먼저 제공하고 지난 예약을
이어 제공하는 기존 혼합 정렬을 유지한다. 웹의 두 탭 건수는 별도 count 응답 필드를
추가하지 않고 각 표시 그룹 Page의 `totalElements`를 사용한다.

조회 응답은 변경, 취소, 완료, 노쇼와 필요한 관리자 조회의 승인 행동마다 독립적인
`allowed`와 `blockedReason`을 제공한다. 이 값은 화면 표시를 위한 Read Model이며 실제
Command는 트랜잭션 실행 시점에 같은 정책을 다시 검증한다. 프론트엔드는 예약 상태와
기기 시각으로 행동 가능 여부를 재구현하지 않는다.

회원에게 반려 사유와 최종 쿠폰 처리 결과를 제공한다. 내부 운영 정보인 관리자 메모, 처리 관리자 식별자, 취소 책임 분류는 노출하지 않는다.

## 쿠폰 임시 점유

예약 신청 시 쿠폰을 차감하지 않지만, 선택된 쿠폰의 사용 가능 횟수 1회를 임시 점유한다. 따라서 잔여 1회인 쿠폰으로 여러 승인대기 예약을 만들 수 없다.

- 신청: 만료일이 가장 가까운 유효 쿠폰에서 1회 임시 점유
- 관리자 승인: 임시 점유를 확정 예약 점유로 전환
- 반려 또는 마감 전 취소: 임시 점유 해제
- 수업 완료: 실제 1회 차감
- 노쇼·마감 후 취소: 관리자 결정에 따라 차감 또는 반환

쿠폰 예약은 `coupon_action`으로 `DEDUCT` 또는 `RETURN`만 허용한다. 이미 존재하는 임시 점유를 반드시 차감 또는 반환으로 종결해야 하므로 `NONE`은 허용하지 않는다.

1회 결제 예약은 `coupon_action`으로 `NONE`만 허용한다. 쿠폰이 존재하지 않으므로 `DEDUCT`와 `RETURN`은 허용하지 않는다.

회원에게 선택된 쿠폰, 만료일, 현재 잔여 횟수와 점유 후 사용 가능 횟수를 보여준다.

## 동일 회원의 수업 구간 중복 예약

- 하나의 회원 계정은 한 명의 실제 기승자를 나타내며 다른 가족 구성원을 대신 예약하지 않는다.
- 동일 회원은 같은 날짜에 실제 수업 구간이 겹치는 활성 예약을 두 개 이상 가질 수 없다.
- 활성 예약은 `pending_admin_approval`, `pending_payment`, `confirmed`다.
- 구간은 `[startTime, endTime)`이며 `existingStartTime < candidateEndTime AND candidateStartTime < existingEndTime`이면 겹친다.
- 종료 시각과 다음 수업 시작 시각이 같은 경우는 겹치지 않는다.
- 클래스나 장소가 달라도 같은 회원의 활성 예약 전체에 적용한다.
- `member_id`, `lesson_date` 단위의 직렬화 행, Application overlap 검사와 exact-start MySQL UNIQUE를 함께 사용해 동시 요청에서도 불변식을 지킨다.
- 실제 겹치는 활성 예약이 확인되면 선검사, 동시성 경쟁과 exact-start UNIQUE 재검증 경로에서 `RESERVATION_OVERLAPPING_ACTIVE_RESERVATION`과 `409 Conflict`를 반환한다.
- overlap 잠금 조회는 DB generated column인 `active_slot_guard = 1`을 활성 상태 조건의 SSOT로 사용하고 같은 상태 목록의 `status IN`을 중복 적용하지 않는다.
- Java의 활성 상태 집합과 DB generated expression은 모든 ReservationStatus를 순회하는 MySQL 계약 테스트로 일치 여부를 검증한다.
- 기존 `RESERVATION_DUPLICATE_ACTIVE_TIME_SLOT`은 신규 API 응답에서 사용하지 않고 호환 기간 동안 내부 상수로만 유지한 뒤 제거한다.

## 예약 생성 요청 멱등성

- 회원 예약 생성과 관리자 수동 예약 생성은 Horse API 계약의 `Idempotency-Key` 요청 헤더를 사용한다.
- 키 범위는 인증 주체와 API 작업 단위이며 회원 생성과 관리자 수동 생성은 서로 다른 범위다.
- 같은 키와 같은 요청 본문은 최초 성공 결과를 반환하고, 같은 키에 다른 본문을 사용하면 `409 Conflict`로 거부한다.
- 요청 fingerprint와 최초 성공 결과를 저장하며 실패 결과는 저장하지 않는다.
- 예약 생성, 쿠폰 점유와 멱등성 완료 기록은 하나의 DB 트랜잭션으로 원자적으로 커밋한다.
- 비즈니스 변경 커밋과 멱등성 완료 기록 사이에 분리된 커밋 구간을 두지 않는다.
- 멱등성 기록의 기본 보관 기간은 24시간이며 정리 Job은 보관 데이터만 정리하고 API 판정을 대신하지 않는다.

## 쿠폰

- 종류는 일반, 마장마술, 장애물 10회권이다.
- 동일 종류의 쿠폰을 여러 장 보유할 수 있다.
- 예약 클래스와 쿠폰 종류가 일치해야 한다.
- 여러 쿠폰이 유효하면 이미 사용 중이라 만료일이 있는 쿠폰을 미사용 쿠폰보다 먼저 선택한다.
- 자동 선택 순서는 만료일이 빠른 순, 등록일이 오래된 순, 쿠폰 ID가 작은 순이다. 등록일과 ID는 결정적인 결과를 위한 tie-breaker다.
- 미사용 쿠폰은 기존 사용 중 쿠폰을 모두 사용한 후 FIFO로 선택한다.
- 첫 번째 쿠폰 수업이 `completed`가 된 수업일을 첫 기승일로 정한다.
- 첫 기승일부터 3개월 동안 유효하다.
- 수업일이 만료일 이후면 예약할 수 없다.
- 예약 당시 정상적으로 쿠폰 1회가 임시 점유된 기존 예약은 이후 첫 사용으로 계산된 만료일을 초과하더라도 유지하며 완료 시 차감한다. 이는 데이터 이관, 관리자 예외, 정책 변경 상황에서 일관성을 유지하기 위한 방어 규칙이다.
- 만료일 계산 이후 생성하는 신규 예약이나 예약 변경은 계산된 만료일 이후 수업을 선택할 수 없다.
- 만료된 잔여 횟수는 소멸하며 차감 대상으로 사용하지 않는다.
- 쿠폰마다 무료 변경권 1회를 가진다.
- 1회 결제 예약은 쿠폰을 생성하거나 차감하지 않는다.

## 가족 그룹과 쿠폰 공유

- FamilyGroup은 안정적인 Group ID로 식별한다. 관리자 구분용 이름은 필수이며 중복을 허용한다.
- 대표 회원, 소유 회원과 회원별 가족 관리 권한은 두지 않는다. 생성·구성원 추가·제거·해제는 ADMIN만 수행한다.
- 회원은 동시에 하나의 활성 FamilyGroup에만 속할 수 있고 가족에 속하지 않은 상태도 허용한다.
- 빈 ACTIVE 그룹을 허용한다. 생성 직후 구성원이 없어도 되고 마지막 구성원 제거는 그룹을 자동 해제하지 않는다.
- 구성원 제거는 해당 membership만 종료한다. 그룹 해제는 관리자가 명시적으로 수행하는 비가역적 종료이며 모든 active membership을 종료한다.
- MVP 3.2는 전용 가족 이관 기능을 제공하지 않는다. 가족 변경은 기존 membership 제거와 새 membership 추가를 독립된 관리자 행위로 수행하며 그 사이 가족이 없는 상태를 허용한다.
- Coupon 레코드와 원소유자는 유지하며 가족 쿠폰 하나로 합치지 않는다. membership은 신규 예약에서 사용할 수 있는 후보 범위만 확장한다.
- 활성 가족 구성원은 같은 활성 그룹 구성원이 소유한 모든 유효 Coupon을 사용할 수 있다. 그룹 가입 전에 발급된 Coupon도 포함한다.
- 후보 Coupon은 예약 클래스·종류가 일치하고 active이며 `remainingCount > heldCount`이고 수업일에 유효해야 한다.
- 가족 전체 후보는 `(expiresAt IS NULL) ASC`, `expiresAt ASC`, `createdAt ASC`, `couponId ASC`로 선택한다. 무기한 Coupon은 마지막이다.
- 구성원 제거나 그룹 해제는 기존 Reservation과 hold를 취소하거나 다른 Coupon으로 교체하지 않는다. 취소·반환은 원래 hold된 Coupon에 적용한다.
- 과거 사용 이력은 예약 회원, Coupon 원소유자, 실제 Coupon, 사용 당시 FamilyGroup, Reservation, 행위, 시각과 actor를 snapshot으로 보존한다.
- 그룹 생성·구성원 추가·제거·해제는 관리자, 시각, 전후 상태와 필수 사유를 추가 전용 감사 이력으로 남긴다. 과거 관계와 사용 이력은 다시 쓰지 않는다.

## 클래스와 탑승 이력

일반 기승 완료 횟수만 일반 클래스 등급에 반영한다. 마장마술과 장애물 완료 횟수는 별도 이력으로 집계한다.

- 실제 완료 일반 기승 횟수는 사실 기록이다. 회원의 실력을 인정하기 위해 타지 않은 횟수를 이 값에 추가하지 않는다.
- `progression baseline`은 기존 경력의 최소 시작점을 인정하는 Anchor다. 영구 class override가 아니며 이후 완료 기승에 따라 자동 승급한다.
- baseline 설정 시 지정 시작 클래스, 그 클래스의 최소 threshold와 설정 당시 실제 일반 기승 횟수를 의미적으로 고정한다.
- baseline 인정분은 `max(0, baselineThreshold - baselineActualRideCount)`로 파생한다. 별도 progression 누적 counter는 두지 않는다.
- baseline이 있으면 progression 값은 현재 실제 일반 기승 횟수에 파생 인정분을 더하고, 없으면 실제 일반 기승 횟수만 사용한다. 명시적인 threshold 순서로 `progressionClass`를 계산한다.
- baseline은 설정·변경·해제할 수 있다. 하향 변경과 해제는 일반 강등이 아니라 잘못된 경력 인정의 교정이며 결과 클래스가 낮아질 수 있다.
- 시스템 도입 이전 경력은 시작 클래스 baseline으로 종결한다. 과거 횟수·날짜·기간을 복원하거나 이후 기승 횟수 보정으로 progression에 다시 넣지 않는다.
- 회원별 Horse progression 관리 시작 이후에는 Horse가 기록한 일반 기승 완료와 그 집계 오류 보정만 progression에 반영한다. 기존 회원의 최초 baseline 승인은 이 관리 시작 경계를 함께 확정한다.
- `promotion hold`는 특수 승인이 없는 회원에게 관리자가 `progressionClass` 이하의 일반 클래스로 설정하는 안전 상한이다. hold 중에도 실제 횟수와 progression은 계속 누적한다.
- `effectiveClass`는 hold가 없으면 `progressionClass`, 있으면 명시적인 클래스 순서상 `progressionClass`와 hold class 중 낮은 값이다.
- 일반 클래스 예약 가능 범위와 등급 표시는 실제 횟수나 JWT가 아니라 `effectiveClass`를 기준으로 판정한다.
- promotion hold는 자동 만료하지 않는다. 변경·해제하면 즉시 현재 누적 progression에 다시 적용하며 중간 클래스를 강제로 거치지 않는다.
- baseline과 promotion hold는 동시에 존재할 수 있다. baseline은 progression 시작점을, hold는 실제 예약 판단에 사용하는 클래스 상한을 담당한다.
- 마장마술 또는 장애물 특수 승인은 progression을 바꾸지 않는 별도 예약 자격이다. 승인 하나라도 있으면 일반 클래스는 `progressionClass`와 대마장 속보 중 높은 범위까지 가능하고 해당 승인 특수 클래스를 추가한다. 특수 승인만으로 구보초보·구보는 열리지 않는다.
- 특수 승인과 promotion hold는 동시에 활성화할 수 없다. hold가 있으면 승인 전에 명시적으로 해제하고, 승인이 있으면 모두 해제한 뒤 hold를 설정한다. 시스템이 어느 쪽도 자동 해제하지 않는다.
- 기승 횟수 보정은 회원별 Horse progression 관리 시작 이후 집계한 완료의 누락·중복 같은 사실 오류만 담당한다. 양수·음수 delta, before, after, 관리자, 시각과 필수 사유를 남기며 결과는 0 이상이다.
- baseline 설정·변경·해제, promotion hold 설정·변경·해제, 특수 승인 변경과 기승 횟수 보정은 전후 상태를 추가 전용 감사 이력으로 남긴다. 기존 완료 수업·예약·Coupon 이력은 다시 쓰지 않는다.

## 타임별 일괄 출석 처리

- 관리자는 같은 수업 날짜와 시작 시각의 예약을 최대 8건까지 한 요청으로 처리한다.
- 각 예약의 처리 유형은 출석 완료(`complete`) 또는 노쇼(`no_show`)다.
- 출석 완료는 기존 단건 완료 정책을 적용하고, 노쇼는 예약 유형에 맞는 `coupon_action`과 최대 500자의 필수 관리자 메모를 적용한다.
- 요청한 날짜·시각과 현재 예약 일정이 다르면 해당 예약만 실패한다.
- 각 예약은 독립 트랜잭션으로 처리한다. 한 예약의 실패는 다른 예약의 성공을 롤백하지 않는다.
- 구조적으로 유효한 요청은 항목별 성공·실패, 최종 상태 또는 오류 정보를 반환한다.
- 반복 요청은 기존 완료·노쇼 멱등성에 따라 쿠폰, 기승 횟수, 노쇼 이력을 중복 반영하지 않는다.

## 예약 변경

변경 마감은 수업 전날 21:00이다.

마감 전은 `Asia/Seoul` 기준 현재 시각이 수업 전날 21:00보다 이른 경우다. 정확히 21:00부터는 마감 후로 판정하며, 평일·주말은 수업일의 요일을 기준으로 구분한다.

- 마감 전: 날짜와 시간 변경 가능, 쿠폰 차감 및 무료 변경권 사용 없음
- 마감 후 무료 변경권 보유: 날짜와 시간 변경 가능, 무료 변경권 사용
- 마감 후 무료 변경권 미보유: 평일에 한해 같은 날의 다른 시간으로만 변경 가능
- 평일 당일 내 시간 변경: 무료 변경권을 사용하지 않음
- 주말 당일 변경: 불가

변경 대상 시간대의 정원을 다시 검증하고 성공 시 기존 정원을 해제한다.

변경은 기존 Reservation의 날짜와 시간만 바꾸며 예약 상태, 결제 방식, 연결 쿠폰, 승인 신청 시각, 입금 마감 시각을 유지한다. 따라서 입금대기 2시간과 승인대기 경고는 최초 예약 신청 시각을 기준으로 계속 계산한다. 관리자 변경도 같은 변경 가능 정책을 적용하고 관리자 메모를 필수로 기록한다.

## 예약 취소

- 마감 전: 쿠폰 점유 반환 또는 1회 결제 취소
- 마감 후 회원 사유: 기본 차감
- 마장 사유: 반환
- 노쇼: 기본 차감
- 관리자 처리: 예약 유형별 허용 범위 안에서 쿠폰 처리를 직접 선택하고 사유 메모 필수

관리자 취소 preview는 선택한 책임에 따른 기본 쿠폰 처리를 권고한다. 마장 책임(`stable`)과 운영 예외(`exception`)의 쿠폰 예약은 `return`, 회원 책임(`member`)의 쿠폰 예약은 마감 전 `return`·마감 후 `deduct`를 권고한다. 관리자는 실행 시 예약 유형별 허용 범위 안에서 권고와 다른 최종 처리를 선택할 수 있다.

회원 질병처럼 회원 사유지만 마장이 예외를 허용할 수 있으므로 최종 쿠폰 처리는 관리자가 결정한다.

회원이 직접 취소하면 활성 예약은 즉시 `cancelled`로 전이한다. 회원 직접 취소의 책임은 `member`로 기록하며 쿠폰 예약은 마감 전 `return`, 마감 후 `deduct`, 1회 결제 예약은 항상 `none`을 적용한다. 예외 반환이 필요한 회원은 관리자가 취소 처리하도록 요청한다.

회원 취소 화면은 실행 전에 서버의 취소 preview를 조회해 예상 쿠폰 처리를 표시한다. preview와 실제 취소는 동일한 정책 판정기를 사용하며, 실행 시점의 판정이 최종 결과다.

## 입금대기

- 유효한 클래스 일치 쿠폰이 없을 때 1회 결제 입금대기로 신청한다.
- 신청 후 2시간과 수업 시작 중 먼저 도래한 시점까지 정원을 점유한다.
- 만료 경계 전에 관리자가 입금을 확인하면 예약을 확정한다.
- 먼저 도래한 만료 경계에 도달하면 `payment_expired`로 바꾸고 정원을 반환한다.
- 회원에게 만료 후 관리자에게 연락하라는 안내를 표시한다.
- 관리자는 만료 예약을 복구할 수 있지만 현재 정원이 남아 있을 때만 가능하다.
- 자동 만료는 Spring Scheduler가 애플리케이션 Service를 직접 호출해 실행한다.
- 관리자는 운영상 필요할 때 `POST /api/admin/jobs/expire-pending-payments`로 동일한 만료 작업을 수동 실행할 수 있다.
- 자동 실행과 수동 실행은 같은 트랜잭션·잠금·멱등성 규칙을 사용한다.
- `payment_expired`는 운영 자동화 상태이며 최종 결제 실패 판정이 아니다. 늦은 입금 확인 시 관리자는 정원을 재확보할 수 있는 경우 예약을 복구한다.
- M1에서는 시스템 역할을 추가하지 않으며 관리자 수동 실행은 `ROLE_ADMIN`으로 제한한다.
