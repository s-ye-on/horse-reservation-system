# ADR 006: 입금대기 만료의 자동·수동 실행 경계

## 상태

`ACCEPTED`

## 배경

입금대기 예약은 신청 후 2시간이 지나면 자동으로 `payment_expired`가 되어 정원을 반환해야 한다. 동시에 관리자가 입금을 늦게 확인할 수 있으므로 만료는 최종적인 결제 실패 판정이 아니며, 관리자는 정원이 남아 있을 때 예약을 복구할 수 있어야 한다.

M1은 단일 Spring Boot 애플리케이션으로 운영하며 외부 배치 서버, 외부 Scheduler, 서비스 간 머신 인증을 사용하지 않는다. 자동 실행과 관리자 수동 실행이 서로 다른 만료 규칙을 가지면 상태와 정원 처리 결과가 달라질 위험이 있다.

## 결정

입금대기 만료의 업무 규칙과 트랜잭션은 `PendingPaymentExpiryService` 하나가 소유한다.

- Spring `@Scheduled` 진입점은 HTTP를 거치지 않고 Service를 직접 호출한다.
- 관리자는 `POST /api/admin/jobs/expire-pending-payments`로 같은 Service를 수동 실행할 수 있다.
- 수동 실행 API는 기존 `/api/admin/**` 보안 경계에 따라 `ROLE_ADMIN`만 호출할 수 있다.
- 자동·수동 실행은 동일한 `Clock`, 만료 대상 조회, 예약 잠금, 상태 전이 규칙을 사용한다.
- Service는 `payment_due_at <= now`인 `pending_payment`만 `payment_expired`로 전이한다.
- 예약 행 잠금과 상태 재검증으로 중복 실행 및 관리자 확정과의 경쟁을 멱등하게 처리한다.
- `payment_expired`는 운영 자동화 상태이며 관리자는 별도 복구 유스케이스로 정원을 다시 확보한 뒤 예약을 복구할 수 있다.

M1에는 `ROLE_SYSTEM`을 도입하지 않는다. 외부 Scheduler나 별도 서비스가 HTTP로 작업을 호출해야 할 때 머신 인증과 함께 재검토한다.

## 검토한 대안

### 외부 HTTP Scheduler와 ROLE_SYSTEM

- 머신 호출 권한을 관리자 권한과 분리할 수 있다.
- 현재 존재하지 않는 토큰 발급·회전·폐기와 외부 실행 인프라를 추가해야 한다.
- M1의 단일 애플리케이션 범위보다 운영 복잡도가 크다.

### 인프로세스 Scheduler와 ADMIN 수동 실행

- 자동 실행은 네트워크와 인증 없이 애플리케이션 내부에서 수행한다.
- 관리자는 기존 JWT 권한 경계에서 운영상 재실행할 수 있다.
- 두 진입점이 같은 Service를 사용하므로 규칙과 트랜잭션이 일치한다.
- 여러 애플리케이션 인스턴스에서는 DB 잠금과 멱등 상태 전이가 반드시 필요하다.

### 관리자 수동 실행만 제공

- 구현은 단순하지만 2시간 자동 만료 정책을 보장하지 못한다.
- 운영자가 실행을 놓치면 정원이 계속 점유되므로 채택하지 않는다.

## 결과

- Scheduler는 얇은 adapter이며 트랜잭션을 열거나 예약 상태를 직접 변경하지 않는다.
- 관리자 Controller도 요청을 Service에 위임하고 별도 만료 로직을 갖지 않는다.
- 만료 실행 주기는 운영 설정값으로 두며 업무 경계 시각은 `Asia/Seoul` Clock으로 판정한다.
- 자동 만료 실패는 다음 실행에서 재시도할 수 있고, 수동 실행도 같은 멱등 경로를 사용한다.
- 외부 Scheduler 도입 시에만 `/api/jobs/**`와 `ROLE_SYSTEM` 또는 별도 머신 인증을 다시 검토한다.

## 검증

- 수업 결제 마감 직전·정각·직후 경계를 고정 Clock으로 검증한다.
- 자동 실행과 ADMIN 수동 실행이 같은 결과를 만드는지 검증한다.
- MEMBER와 미인증 사용자가 수동 실행 API를 호출할 수 없는지 검증한다.
- 동시 만료, 반복 만료, 만료와 관리자 확정 경쟁에서 상태 전이가 한 번만 발생하는지 MySQL 통합 테스트로 검증한다.
- 만료 예약이 정원 집계에서 제외되고 후속 복구 대상이 되는지 검증한다.
