# ADR 010: 일괄 출석 처리의 항목별 트랜잭션 경계

## 상태

`ACCEPTED`

## 배경

관리자는 한 수업 시간대의 여러 예약을 출석 완료 또는 노쇼로 처리해야 한다. 한 예약의 상태나 쿠폰 요청이 잘못되었다는 이유로 이미 유효하게 처리할 수 있는 다른 예약까지 실패하면 운영자가 원인을 찾고 다시 처리하기 어렵다. 반대로 한 트랜잭션 안에서 예외를 잡고 계속 처리하면 rollback-only 상태와 영속성 컨텍스트 오염으로 실제 커밋 결과를 신뢰하기 어렵다.

기존 단건 `ReservationCompletionService`와 `ReservationNoShowService`는 예약 행을 잠그고 상태 전이, 쿠폰 처리, 기승 횟수 또는 노쇼 이력을 하나의 트랜잭션으로 처리하며 반복 호출에 멱등하다.

## 결정

- 일괄 Application Service는 트랜잭션을 열지 않고 요청 항목을 순서대로 조정한다.
- 각 항목은 별도 Spring Bean의 `REQUIRES_NEW` 트랜잭션에서 처리한다.
- 항목 처리기는 예약을 `PESSIMISTIC_WRITE`로 잠그고 요청의 수업 날짜·시각과 현재 예약 일정이 같은지 검증한다.
- 일정 검증 후 기존 단건 완료 또는 노쇼 Service를 호출한다. 두 Service는 항목 트랜잭션에 참여하므로 상태와 쿠폰·회원·감사 이력 변경이 항목 단위로 함께 커밋되거나 롤백된다.
- 구조적으로 유효한 일괄 요청은 HTTP 200을 반환하고 각 항목에 성공 여부, 최종 상태 또는 오류 코드·메시지를 제공한다.
- 업무 예외와 예기치 않은 실행 예외는 실패한 항목 결과로 격리한다. 예기치 않은 예외는 외부에 내부 정보를 노출하지 않는 공통 오류 코드로 반환한다.
- 잘못된 요청 본문, 인증 실패, 권한 실패는 항목 처리 전에 기존 전역 오류 응답으로 거부한다.
- 별도의 일괄 실행 엔티티나 원장은 만들지 않는다. 예약·쿠폰·변경 이력이 현재 상태와 행위의 SSOT다.

## 검토한 대안

### 요청 전체를 하나의 트랜잭션으로 처리

구현은 단순하지만 한 항목 실패가 전체를 롤백해 M3-04의 부분 성공 요구를 충족하지 못한다.

### 하나의 트랜잭션에서 예외를 잡고 계속 처리

트랜잭션이 rollback-only가 되거나 영속성 컨텍스트에 실패 상태가 남을 수 있어 응답의 성공 결과와 실제 커밋 결과가 달라질 수 있다.

### 일괄 실행 원장 추가

재시도와 장기 실행 추적에는 유용하지만 현재 최대 8건의 동기 관리자 요청에는 별도 영속 모델의 비용이 더 크다. 비동기 실행, 재개 가능한 작업, 실행 단위 감사 요구가 생길 때 재검토한다.

## 결과

- 한 항목 실패가 앞뒤 항목의 성공을 롤백하지 않는다.
- 이미 완료 또는 동일 노쇼로 처리된 예약을 다시 요청해도 기존 단건 멱등성에 따라 부수 효과를 중복 반영하지 않는다.
- 일괄 API와 단건 API가 같은 도메인 상태 전이와 쿠폰 정책을 사용한다.
- 항목 트랜잭션은 순차 실행하므로 같은 예약을 중복 포함하거나 반복 요청해도 예약 잠금 순서가 결정적이다.
- 호출자는 부분 성공 응답을 확인하고 실패한 항목만 보정할 수 있다.

## 검증

- 성공 항목과 상태 오류 항목을 함께 요청해 성공 항목만 커밋되는지 검증한다.
- 다른 날짜·시간의 예약이 포함되면 해당 항목만 실패하는지 검증한다.
- 같은 요청을 반복해 쿠폰 차감, 회원 기승 횟수, 노쇼 감사 이력이 한 번만 반영되는지 검증한다.
- 최대 항목 수와 관리자 권한, 요청 본문 검증을 API 테스트로 확인한다.
