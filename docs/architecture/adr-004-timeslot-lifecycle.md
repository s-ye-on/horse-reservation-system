# ADR 004: TimeSlot 운영 상태와 데이터 생명주기 분리

## 상태

확정, ADR-015가 날짜 운영과 자동 occurrence 범위를 부분 대체

## 맥락

시간대 운영 마감과 잘못 생성된 데이터 정리를 같은 삭제 동작으로 처리하면 신규 예약 차단, 기존 예약 보존, 감사 데이터 삭제의 의미가 섞인다. 현재 TimeSlot은 `is_closed`를 저장하며 예약은 별도 도메인이 소유한다.

## 검토한 대안

1. `DELETE`를 마감 처리의 별칭으로 사용한다. 구현은 단순하지만 `PATCH`와 중복되고 오생성 데이터를 정리할 수 없다.
2. `close_reason` enum을 TimeSlot 현재 행에 저장한다. 마지막 사유는 표시할 수 있지만 재개와 재마감 이력이 사라져 감사 기록이 되지 않는다.
3. 운영 상태 변경과 물리 삭제를 분리하고, 사유 감사가 필요할 때 별도 상태 변경 이력을 추가한다.

## 결정

- `PATCH /api/admin/timeslots/{id}`는 `is_closed`만 변경한다.
- 닫힌 시간대는 신규 예약을 허용하지 않지만 기존 예약을 변경하거나 삭제하지 않는다.
- `DELETE /api/admin/timeslots/{id}`는 잘못 생성된 시간대를 정리하는 물리 삭제다.
- 예약 또는 예약 이력이 존재하면 `409 Conflict`로 삭제를 거부한다.
- 삭제 가능성은 TimeSlot application port로 조회하고 예약 영속화 시 reservations adapter가 구현한다.
- `close_reason`은 현재 범위에서 제외하고 감사 요구가 생기면 별도 상태 변경 이력으로 설계한다.
- TimeSlot은 독립 도메인이므로 업무 오류는 `TIMESLOT_*` 접두사를 사용한다.

ADR-015 이후 이 결정은 개별 TimeSlot 휴강에 적용한다. 날짜 전체 휴무,
정규 시간표, 정기 휴일과 자동 occurrence의 생명주기는 ADR-015를 따른다. 자동 생성된
TimeSlot은 일반 운영에서 물리 삭제하지 않고 행과 마감 원인을 유지한다.

## 결과

운영 마감과 데이터 생명주기의 의미가 분리되고 기존 예약은 예약 관리 절차에서만 변경된다. 대신 예약 영속화 Task에서 TimeSlot 삭제 가능성 port를 실제 예약 이력 조회에 연결해야 한다.

## 검증

- PATCH가 행을 유지하며 `is_closed`만 변경하는지 검증한다.
- 예약 이력이 없는 시간대만 물리 삭제되는지 검증한다.
- 예약 이력이 있으면 DELETE가 `409 Conflict`인지 검증한다.
- `TIMESLOT_*` 오류가 기존 접두사·중복 하네스를 통과하는지 검증한다.
