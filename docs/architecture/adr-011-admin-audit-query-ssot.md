# ADR 011: 관리자 감사 이력 조회의 SSOT와 읽기 모델

## 상태

`ACCEPTED`

## 배경

MVP-2는 예약 복구, 노쇼, 일정 변경, 취소를 `ReservationChangeLog`에 추가 전용으로 기록하고 쿠폰 점유·확정·사용·반환·만료는 `CouponUsageLog`에 기록한다. 두 원장은 소유 도메인과 필드가 다르며 기존 행을 수정하거나 삭제하지 않는다.

MVP-3 관리자는 회원·예약·기간을 기준으로 예약 변경 이력의 행위자, 사유, 전후 상태와 일정을 조회해야 한다. 이후 다운로드는 예약 변경 이력뿐 아니라 쿠폰 사용 이력도 제공해야 하지만, 조회 편의를 위해 두 원장을 복제하거나 하나의 쓰기 테이블로 합치면 동일 행위가 여러 SSOT에 중복된다.

## 결정

- M3-07 관리자 감사 API는 `ReservationChangeLog`를 예약 행위 감사의 SSOT로 직접 조회한다.
- 조회는 `reservations`와 `members`를 읽기 전용으로 조인해 회원 식별 정보와 회원 이름·전화번호 키워드 필터를 제공한다.
- 필터는 `keyword`, `reservationId`, `occurredDateFrom`, `occurredDateTo`, `actorType`, `changeType`이며 페이지 기본값은 0과 20, 최대 크기는 100이다.
- 기간을 생략하면 모든 예약 변경 이력을 대상으로 한다. 정렬은 `created_at DESC`, `id DESC`로 고정한다.
- 전체 기간 최신순 조회를 위해 `reservation_change_logs(created_at, id)` 인덱스를 추가한다. 기존 예약별 `(reservation_id, created_at, id)` 인덱스는 유지한다.
- 조회 중 예약, 회원, 쿠폰, 감사 행을 변경하지 않는다. 과거 예약의 현재 상태에서 존재하지 않는 이력을 추론하거나 backfill하지 않는다.
- `CouponUsageLog`는 쿠폰 행위의 별도 SSOT로 유지한다. M3-09 다운로드는 두 원장을 각각의 조회 모델로 내보내며 하나의 쓰기 원장으로 합치지 않는다.

## 검토한 대안

### 통합 감사 테이블에 기존 원장을 복제

한 쿼리로 모든 행위를 조회하기 쉽지만 동일 행위가 도메인 원장과 통합 원장에 중복되고, 트랜잭션마다 두 기록의 일관성을 유지해야 한다.

### SQL UNION으로 예약과 쿠폰 이력을 단일 목록으로 반환

화면은 하나가 되지만 예약 전후 상태와 쿠폰 수량 변화의 의미가 달라 nullable 필드가 많아지고, 쿠폰 이력에는 현재 관리자 인증 주체가 저장되지 않아 행위자 계약도 비대칭이다.

### 현재 Reservation 행에서 과거 이력 합성

현재 상태 필드는 마지막 결과만 보존하므로 일정 변경과 반복 처리의 순서를 복원할 수 없다. 감사 이력으로 사용할 수 없다.

## 결과

- 기존 추가 전용 원장의 소유권과 무결성을 유지하면서 관리자 조회를 제공한다.
- 예약 감사 화면과 다운로드가 같은 필터·정렬 계약을 재사용할 수 있다.
- 쿠폰 이력은 별도 원장으로 명확하게 구분되며 M3-09에서 독립적으로 개인정보 제한을 적용할 수 있다.
- 예약 생성·승인·반려·결제 만료·완료처럼 현재 `ReservationChangeLog`가 생성하지 않는 행위는 M3-07이 추론하지 않는다. 해당 행위를 추가 전용으로 기록해야 하는 요구가 생기면 독립 Task로 원장 계약을 확장한다.

## 검증

- 회원·예약·기간·행위자·변경 유형 필터와 고정 정렬을 MySQL API 테스트로 검증한다.
- 미인증과 회원 권한을 거부하고 조회 전후 데이터가 동일한지 검증한다.
- OpenAPI가 Query DTO를 평면 parameter로 생성하는지 검증한다.
- `information_schema.statistics`에서 전체 최신순 인덱스 순서를 검증한다.
