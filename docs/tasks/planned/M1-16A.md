# M1-16A: 관리자 예약 조회 API

## 상태

`READY`

## 목표

관리자가 예약 상태와 운영 판단에 필요한 예약 목록과 상세를 조회한다.

## 담당

`backend`

## 선행 작업

- M1-11, M1-12, M1-13, M1-14, M1-15, M1-16 완료

## 입력 문서

- [제품 요구사항](../../product/requirements.md)의 `관리자 기능`, `정원`
- [MVP 1](../../product/mvp-1.md)의 관리자 승인·반려·복구 범위
- [운영 정책](../../product/policies.md)의 `승인대기 경고`
- [API 초안](../../architecture/api.md)의 `GET /api/admin/reservations`와 상세 조회
- [예약 상태 전이](../../architecture/reservation-state-machine.md)의 상태와 관리자 승인대기 경고
- 경계 입력 원칙: command가 필요하면 command use case 하나만 트랜잭션 owner가 된다. 이 조회 use case는 read-only이며 상태·정원·쿠폰을 변경하거나 command를 우회하지 않는다.
- `backend/conventions/README.md`의 기존 패키지·계층·테스트 규칙

## 제외 범위

- 예약 승인·반려·만료·복구 command 변경
- 입금대기 전용 조회와 회원 본인 예약 조회
- 관리자 예약 변경·취소와 프론트엔드 화면
- 기존 아키텍처·컨벤션 변경과 관련 없는 리팩터링

## 완료 조건

- [ ] ADMIN만 예약 목록과 상세를 조회하고 MEMBER 요청 및 존재하지 않는 예약을 구분해 거부한다.
- [ ] 목록과 상세에 회원·수업·상태·결제원·쿠폰·주요 상태 시각과 승인대기 경고 등 운영 판단 정보를 제공한다.
- [ ] 경고는 `approval_requested_at`, 현재 시각, 수업 시작 시각으로 계산하며 조회가 상태·정원·쿠폰·감사 이력을 변경하지 않는다.
- [ ] 검증 명령이 모두 종료 코드 0으로 성공한다.

## 중단 조건

- 관리자 목록에 필요한 필터·정렬·페이지 계약을 구현 전에 제품 결정해야 한다.
- 승인대기 경고를 저장 상태로 만들거나 조회 중 예약 상태를 변경해야 한다.
- 회원 개인정보 노출 범위를 기존 관리자 권한 정책으로 결정할 수 없다.
- 목록 조회를 위해 command use case나 상태 전이 코드를 수정해야 한다.
- 허용 범위 밖의 스키마·프론트엔드 변경이 필요하다.
