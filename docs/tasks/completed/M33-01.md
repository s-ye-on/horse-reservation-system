# M33-01 Completion Evidence

## 상태

`DONE`

## 목표

Horse 예약 시스템 운영 이후 선택 월의 `COMPLETED` Reservation을 `lessonDate`와 기존
RidingClass 분류로 집계해 관리자에게 총 완료 횟수와 공동 최다 기승 회원 전체를 제공한다.

## 구현 계약

- `GET /api/admin/reservations/monthly-ride-statistics`는 선택 `month`와 `rideType`을 조회한다.
- `month`를 생략하면 공용 `Clock`의 `Asia/Seoul` 현재 월을 사용한다.
- `rideType`은 `ALL`, `GENERAL`, `DRESSAGE`, `JUMPING`이며 생략하면 `ALL`이다.
- `GENERAL`은 `RidingClass.isGeneral()`인 기존 catalog 전체, 특수 종류는 기존 `DRESSAGE`,
  `JUMPING`에서 파생한다. 별도 영속 분류를 만들지 않는다.
- 응답은 조회 월·종류, 총 완료 횟수, 최고 완료 횟수와 최고 횟수를 가진 회원 전체를 반환한다.
  공동 1위는 회원 ID 오름차순으로 결정적으로 정렬하되 누락하지 않는다.
- 0건이면 총·최고 완료 횟수는 0이고 공동 최고 회원 목록은 비어 있다.
- baseline, progression 상태, Member 누적 횟수와 M32-07 correction은 읽거나 집계하지 않는다.

## Query와 DB

- Repository가 `COMPLETED`, 반개구간 월 범위와 RidingClass 집합을 SQL predicate로 적용하고
  Member와 함께 회원별 `count`를 한 번에 projection한다.
- Application Service는 DB가 반환한 회원별 집계 행에서 총합, 최고 횟수와 모든 공동 최고 회원을
  조립한다. Reservation 전체나 Member Entity를 메모리로 읽지 않는다.
- 단일 회원과 21명·101건 fixture 모두 prepared statement 1회로 조회되어 회원·Reservation 수에 따른
  N+1이 없음을 확인했다.
- MySQL `EXPLAIN`에서 `idx_reservations_lesson_status`가 후보로 확인되고 실제 plan은 기존
  `lesson_date` 선두 index의 `range`/`ref` access를 사용해 full scan을 피한다.
- 현재 bounded DB aggregation과 고정 query 수를 위해 새 index가 필요하다는 근거가 없어 migration은
  추가하지 않았다.

## API 응답

```text
month, rideType, totalCompletedRideCount, topCompletedRideCount,
leaders[{ memberId, memberName, completedRideCount }]
```

관리자 bearer 권한은 기존 `/api/admin/**` 보안 경계를 그대로 사용한다. 잘못된 월 형식은 공통 요청
오류, 지원하지 않는 종류는 `RESERVATION_INVALID_MONTHLY_RIDE_TYPE`으로 거부한다.
