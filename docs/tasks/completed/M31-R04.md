## Completion Evidence

### 구현

- `RegularScheduleTemplateService`가 설정 guard를 `FOR UPDATE`로 잠근 뒤 ACTIVE와
  expected version을 검증하고 Template 변경, SYNCING 시작과 감사 로그를 한 트랜잭션에
  반영한다.
- 생성·변경·활성화·비활성화는 물리 삭제 없이 도메인 메서드로 상태를 변경한다.
- 영향 미리보기는 이전·변경 요일, 동일 시각의 기존 MANUAL/TEMPLATE TimeSlot과
  `active_slot_guard = 1`인 예약을 집계한다.
- MySQL 동시 요청에서 create/create와 update/deactivate 중 하나만 성공하고 다른 요청은
  `SCHEDULE_CONFIG_SYNC_IN_PROGRESS`로 종료됨을 검증했다.
- 월요일 정기 휴일 규칙과 월요일 Template이 동시에 존재할 수 있고 기존 MANUAL
  TimeSlot의 정원·마감 원인이 변경되지 않음을 검증했다.

### 독립 검토

- PM: 신규 Template 미리보기의 MANUAL 충돌, 월요일 정기 휴일 공존, 기존 MANUAL
  TimeSlot 불변 증거가 부족하다고 지적했다. 미리보기 SQL과 통합 테스트를 보강했다.
- Architecture: R04 트랜잭션 원자성은 적절하다고 확인했다. 동기화 완료·실패·재시도
  생명주기는 R06 소유이고 R04/R05에는 공개 Controller가 없으므로 R04 범위를 확장하지
  않는다. R06 전환 검토에서 `begin/complete/fail/retry/status` 계약을 필수 차단
  항목으로 다시 확인한다.
- Architecture: 활성 예약 상태 문자열의 중복 정의를 지적했다. 영향 집계는 V15의
  generated `active_slot_guard`를 사용하도록 변경했다.
- DB: 요일 변경 시 이전·신규 날짜 영향 합산, 교차 Command 동시성, 영향 조회 인덱스
  근거가 부족하다고 지적했다. 이전·신규 요일 합산, update/deactivate 경쟁 테스트,
  `template_id` FK 인덱스와 `(lesson_date, start_time)` UNIQUE 인덱스 계약 테스트를
  추가했다.

### 자기 점검

- Controller 또는 공개 API를 추가하지 않았고 Application Service가 트랜잭션과
  orchestration만 담당한다.
- Entity 상태는 `change`, `activate`, `deactivate`, `beginSynchronization`으로
  변경하며 public setter를 추가하지 않았다.
- 새 업무 예외는 `ScheduleException`과 `SCHEDULE_*` 코드를 사용한다.
- Request/Result 모델은 record이며 기존 migration과 기존 TimeSlot을 수정하지 않았다.

## 남은 위험과 후속 소유

- R04는 설정을 SYNCING으로 전환하는 시작 계약만 구현한다. 부분 적용 재개, 실패 기록,
  전체 horizon 확인과 ACTIVE 복귀는 계획대로 M31-R06이 소유한다.
- R05는 R04와 같은 guard·version·audit 계약을 사용해야 한다. 중복 orchestration이나
  별도 상태 전이를 만들면 R06 전환 검토에서 차단한다.
- 활성 예약의 Java enum, V15 `active_slot_guard`와 이후 overlap SQL의 전체 일치 증명은
  M31-R08의 완료 조건으로 유지한다.

## 중단 조건

- Controller나 occurrence 동기화를 조기 구현해야 한다.
- Template 변경이 기존 TimeSlot을 직접 수정해야 한다.
- 정기 휴일 정책 선택이 필요하다.
- 기존 V1~V25 migration 수정이나 데이터 보정이 필요하다.
- 관련 없는 파일 수정이나 기존 검증 완화가 필요하다.
- 같은 원인의 검증 실패가 세 번 반복된다.
