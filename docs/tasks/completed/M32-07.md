# M32-07 Completion Evidence

## 목표

Horse progression 관리 시작 이후 Horse가 관리한 실제 일반 기승 완료 집계 오류를 관리자가
명시적 delta로 정정하고, 직렬화된 전후 상태와 관리자·사유를 append-only로 감사한다.

## Architecture 결정

기존 `member_class_progression_audit_logs`를 클래스 progression 변경의 단일 감사 원장으로
유지한다. 별도 횟수 보정 원장은 같은 상태·관리자·사유를 중복 저장하고, 기존 원장에 nullable
delta column을 추가하는 방식은 특정 action 때문에 범용 감사 schema를 결합하므로 선택하지
않았다.

- 회원 행을 `PESSIMISTIC_WRITE`로 잠근 하나의 transaction에서 before snapshot, actual count
  delta 적용, after snapshot과 감사 append를 순서대로 수행한다.
- 감사 action은 `RIDE_COUNT_ADJUSTED`이며 요청 delta를 action-specific JSON metadata로 명시한다.
- `progressionManagementStartedAt`, baseline snapshot과 `specialApprovalProgressionCredit`은 변경하지
  않는다. 파생 progression/effective class만 기존 M32-06 계산으로 다시 평가한다.
- V39는 기존 감사 원장의 action allowlist만 확장하고 새 counter나 별도 원장을 만들지 않는다.

## 구현

- `Member.adjustGeneralRideCount(delta)`가 progression 초기화 여부, non-zero delta, 0 이상 결과와
  정수 overflow를 검증한 뒤 `generalRideCount`만 변경한다.
- `POST /api/admin/members/{memberId}/class-progression/ride-count-adjustments`는 delta와 최대
  500자의 필수 사유를 받고 변경된 관리자 회원 progression 상태를 반환한다.
- `AdminMemberClassProgressionService`는 `findByIdForUpdate`로 회원 행을 잠근 transaction에서
  before snapshot, domain Command, after snapshot과 감사 append를 수행한다.
- 감사의 `from_state`와 `to_state`는 실제 횟수, progression/effective class, 관리 시작 경계,
  baseline, 특수 승인 인정분과 hold를 보존하며 `to_state.rideCountDelta`에 요청 delta를 명시한다.
- `V39__allow_member_ride_count_adjustment_audit.sql`은 기존 감사 데이터를 변경하지 않고
  `RIDE_COUNT_ADJUSTED` action만 DB allowlist에 추가한다.

## 독립 검토

- Architecture/Domain reviewer가 기존 원장 재사용, 회원 행 잠금, V39 action 확장을 권고했다.
- 별도 원장은 이중 감사와 상태 분산 위험, nullable delta column은 중복 정보와 schema 결합 때문에
  제외했다.
- 최종 구현 diff 재검토 결과 CRITICAL/HIGH/MEDIUM/LOW finding은 없다.
- 첫 검토의 MEDIUM 동시성 finding은 첫 transaction이 회원 잠금을 보유한 채 멈추고 두 번째
  보정이 대기함을 확인하는 전용 통합 테스트로 보정했다.
- LOW 경계 finding은 유효한 음수 delta와 정수 overflow 실패·무감사 시나리오로 보정했다.
