## Completion Evidence

### Migration과 최종 스키마

- V17 Java migration은 공용 read-only SQL로 TimeSlot·Reservation의 NULL, 45분 위반,
  자정 초과, source와 마감 값을 첫 DDL 전에 전수 검사한다. 실패 메시지는 문제 유형,
  테이블·ID, 날짜·시작·종료 시각과 유형별·전체 건수를 포함한다.
- V17은 두 `end_time`을 NOT NULL로 강화하고 45분·당일 종료 CHECK와 시작 시각 기반
  default expression을 적용했다.
- V18~V23은 `regular_schedule_templates`, `recurring_holiday_rules`,
  `schedule_config_guard`, `schedule_dates`, `reservation_member_day_guards`,
  `schedule_audit_logs`를 책임별 migration으로 추가했다.
- V24는 기존 TimeSlot의 `source=MANUAL`을 보존하고 template FK·source 결합 CHECK와
  세 독립 마감 원인을 추가했다.
- V15 `uk_reservations_active_member_slot` 네 컬럼은 migration 계약 테스트에서 그대로
  유지됨을 확인했다.

### `is_closed` 결정

- mutable 파생값보다 DB 불변식이 하나인 stored generated column을 선택했다.
- `is_closed = admin_closed OR recurring_holiday_closed OR template_inactive_closed`다.
- JPA는 generated 값을 읽기 전용으로 매핑하고 도메인 `isClosed()`는 세 원인의 OR을
  즉시 계산하므로 같은 트랜잭션의 API 응답이 refresh에 의존하지 않는다.
- 기존 `changeClosedStatus`와 관리자 PATCH는 `admin_closed`만 변경한다. 기존 닫힌
  행은 admin 원인으로, 열린 행은 세 원인 false로 이관됐다.

### 실제 잠금 계약

| Repository 계약 | 실제 SQL 핵심 | 인덱스 | 트랜잭션 |
|---|---|---|---|
| Config 공유 | `WHERE id = 1 FOR SHARE` | `PRIMARY(id)` | `MANDATORY`, read-only |
| Config 배타 | `WHERE id = 1 FOR UPDATE` | `PRIMARY(id)` | `MANDATORY` |
| 운영 날짜 | `WHERE schedule_date = ? FOR UPDATE` | `uk_schedule_dates_date` | `MANDATORY` |
| 회원·날짜 | PK upsert 후 같은 key `FOR UPDATE` | `PRIMARY(member_id, lesson_date)` | 하나의 `MANDATORY` 메서드 |

- `EXPLAIN FORMAT=JSON`으로 위 세 조회가 지정 인덱스를 선택함을 확인했다.
- 실제 MySQL에서 Config 공유 잠금끼리는 공존하고 공유·배타는 직렬화됐다.
- 같은 ScheduleDate와 member-day key는 직렬화됐고 다른 날짜·회원 key는 대기하지
  않았다.
- member-day guard는 점유나 예약 상태를 저장하지 않으며 복수 key를 회원·날짜
  오름차순으로 획득한다.

### 기존 데이터와 독립 검토

- 첫 운영 preflight는 로컬 demo seed 두 행의 `end_time=NULL`을 정확히 보고하고 중단했다.
  두 행이 같은 demo 실행에서 생성되고 연결 예약이 없음을 읽기 전용으로 확인한 후,
  운영자 보정으로 종료 시각만 10:45로 명시했다. migration은 자동 보정하지 않았다.
- 이후 실제 로컬 DB의 V16→V24 8개 migration과 기존 API 전체 회귀가 통과했다.
- 독립 Architecture 검토 의견에 따라 `is_closed`는 generated 방식으로 단일화하고,
  migration을 책임별 버전으로 분리했으며, Repository는 잠금 primitive만 제공하고
  후속 Command를 연결하지 않았다.
- `ScheduleAuditLog`는 `append`와 read만 제공하며 update/delete 경로가 없다.

## 남은 위험과 후속 범위

- MySQL DDL은 원자 rollback되지 않는다. V17 또는 V24 중간 장애 시
  `information_schema`와 Flyway 이력을 확인해 forward-complete 또는 명시적 원복 후
  `flyway repair`해야 한다.
- ScheduleDate 3개월 horizon과 과거 날짜 보존 실행은 R03으로 넘겼다.
- Template·정기 휴일 전이와 `SYNCING` workflow는 R04~R06으로 넘겼다.
- 예약 3시간 마감과 member-day guard를 실제 overlap Command에 연결하는 작업은
  R07·R08로 넘겼다.
- 날짜·개별 TimeSlot 휴무 정리, Controller, OpenAPI, 웹과 Expo는 R09 이후 범위다.
- RecurringHolidayRule 기간 overlap의 Application·동시성 방어는 R05 책임이며 R02
  Repository가 조기 구현하지 않았다.
