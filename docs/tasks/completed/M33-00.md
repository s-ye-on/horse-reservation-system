# M33-00 Completion Evidence

## 상태

`DONE`

## 목표

MVP 4 이전 관리자 운영 가시성 Phase의 월간 완료 기승 통계와 주간 운영 캘린더 정책, read model
경계와 구현 순서를 확정한다.

## 확정 계약

- 월간 기승 현황은 Horse 예약 시스템 운영 이후 선택 월의 `COMPLETED` Reservation을
  `lessonDate`로 집계한다.
- `ALL`, `GENERAL`, `DRESSAGE`, `JUMPING`은 기존 RidingClass를 배타적으로 분류하며 총 횟수와
  공동 최고 회원 전체를 같은 기준으로 계산한다.
- progression 상태, Member 누적 횟수, M32-07 correction과 Horse 운영 이전 경력은 월간 운영
  실적에 포함하지 않는다.
- 주간 캘린더는 materialized TimeSlot을 root로 사용해 빈 TimeSlot도 반환하고 같은 슬롯의 회원,
  RidingClass와 원래 ReservationStatus를 함께 제공한다. 표시 대상은 정원을 점유하는
  `PENDING_ADMIN_APPROVAL`, `PENDING_PAYMENT`, `CONFIRMED`와 실제 수업 기록인 `COMPLETED`다.
- `PAYMENT_EXPIRED`, `APPROVAL_EXPIRED`, `REJECTED`, `CANCELLED`, `NO_SHOW`는 기본 주간 캘린더에서
  제외하고 기존 관리자 예약 조회와 해당 상태 전이에 대해 존재하는 감사 조회의 책임으로 유지한다.
  표시 대상이 없으면 제외 이력이 있어도 `예약 없음`으로 표현한다.
- TimeSlot별 반복 HTTP 요청, Frontend 집계, mutable 통계 counter, snapshot table와 correction
  실제 수업일은 도입하지 않는다.
- M33-01~02 Backend read API, M33-03 OpenAPI/generated client, M33-04~05 Web, M33-06 최종 Gate로
  작업을 분리하고 MVP 4 전체를 M33-06 이후로 이동한다.

## 독립 검토

- Product/Domain: 월간 계약은 기존 완료·progression SSOT와 일치한다. 주간 요구는 기존 API 재사용이
  아니라 전용 read model이 필요하고 MVP 4 전체 후행은 문서 의존성 갱신이 필요하다고 판단했다.
- Backend/Data: Reservation과 RidingClass만으로 mutable truth 없이 월간 집계가 가능하고,
  TimeSlot과 Reservation/Member의 7일 bounded query로 주간 조회가 가능하다고 판단했다.
- Admin Web/UX: 기존 flat upcoming TimeSlot 목록은 현재 주의 지난 슬롯과 예약 상세를 제공하지
  않으므로 전용 주간 API와 반응형 주간 View가 필요하다고 판단했다.
- 최종 anti-overengineering/completeness 재검토: CRITICAL/HIGH/MEDIUM/LOW finding 없음.
- 2026-08-25 계약 명확화: “모든 기존 상태 표시”로 읽히던 표현을 기존 정원 점유 SSOT와
  `COMPLETED`의 합으로 교체했다. 예약 상태나 production 정원 정책은 변경하지 않았다.
