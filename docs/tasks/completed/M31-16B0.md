# M31-16B0: 웹 인증 Cookie·CSRF 계약

## 상태

`DONE`

## 목표

기존 JSON Token API와 인증 상태 전이를 유지하면서 웹 전용 API에는 Access Token JSON과
HttpOnly Refresh Cookie, stateless CSRF와 정확한 CORS allowlist를 제공한다.

## 담당

`backend | security | qa | docs`

## 선행 작업

- M31-16A
- M31-16A2

## 제외 범위

- DB schema와 Flyway migration
- React 인증 UI·AuthProvider·보호 Route·Token 저장 구현
- 자동 refresh·single-flight·동시 401·다중 탭 조정
- 웹 signup Endpoint와 회원가입 자동 로그인
- XSS sanitizer/filter/CSP, rate limit, 비밀번호 재설정
- M31-16B1·B2, M31-17과 관련 없는 리팩터링

## 완료 조건

- [x] 기존 `/api/auth/**` JSON Token API와 Bearer `/me` 계약을 유지한다.
- [x] 웹 login·refresh는 Access Token만 JSON으로 반환하고 Refresh Token은 HttpOnly Cookie로 발급·회전한다.
- [x] 웹 logout은 Session을 멱등 정리하고 같은 속성의 Refresh Cookie를 삭제한다.
- [x] 웹 변경 Endpoint는 stateless CSRF로 보호되며 실패는 공통 403 ErrorResponse다.
- [x] 개발·운영 Cookie Secure와 exact CORS allowlist 계약을 검증한다.
- [x] OpenAPI와 생성 Client에 Refresh 원문 없는 웹 계약이 결정적으로 생성된다.
- [x] `JSESSIONID`가 생성되지 않으며 관련 검증 명령이 모두 성공한다.

## 구현 증거

### 기존 API와 웹 Endpoint

- 기존 `/api/auth/signup`, `/api/auth/login`, `/api/auth/refresh`, `/api/auth/logout`,
  `/api/auth/me`의 JSON Token·Bearer 계약은 변경하지 않았다.
- 웹 전용 `GET /api/auth/web/csrf`, `POST /api/auth/web/login`,
  `POST /api/auth/web/refresh`, `POST /api/auth/web/logout`만 추가했다.
- 웹 login·refresh 응답 DTO에는 Access Token, token type, Access Token 만료 시각만 존재한다.
  Refresh Token 원문은 JSON, OpenAPI schema와 로그에 포함되지 않는다.
- 웹 Application Service는 기존 `AuthSessionService`에 위임하여 login, rotation,
  `FAMILY_REVOCATION`, 단일 Session logout 상태 전이를 재사용한다.

### Cookie·CSRF·CORS

- Refresh Cookie는 `HORSE_REFRESH_TOKEN`, `HttpOnly=true`, `SameSite=Lax`, host-only,
  `Path=/api/auth/web`, Refresh Session TTL과 같은 `Max-Age`를 사용한다.
- `prod`에서는 `Secure=true`, 로컬 HTTP 개발에서는 `Secure=false`이며 발급·회전·삭제가
  name, Path, SameSite, Secure 속성을 동일하게 사용한다.
- Spring Security SPA CSRF와 `CookieCsrfTokenRepository` 기본 계약을 사용한다.
  브라우저는 먼저 CSRF 초기화 Endpoint를 호출하고 `XSRF-TOKEN` Cookie 값을
  `X-XSRF-TOKEN` Header로 login·refresh·logout에 전달한다.
- 두 SecurityFilterChain 모두 `SessionCreationPolicy.STATELESS`이며 웹 통합 테스트에서
  `JSESSIONID`가 생성되지 않음을 확인했다.
- 웹 인증 경로의 CORS는 credential 요청을 허용하되 개발 Origin을
  `http://localhost:5173`으로 한정한다. 운영 Origin은 `WEB_ALLOWED_ORIGINS` 외부 설정으로
  주입하며 literal wildcard는 설정 단계에서 거부한다.
- 허용된 웹 Endpoint만 익명 접근을 허용하고 같은 prefix의 알 수 없는 Endpoint는 거부한다.

### 실패·멱등 계약

- CSRF 실패는 기존 공통 `ErrorResponse` 형식의 403으로 반환한다.
- 웹 refresh의 잘못된 Cookie는 Cookie를 삭제한 뒤 기존 공통 401을 반환한다.
- `ROTATED` Token 재사용 시 M31-16A2의 동일 트랜잭션 family 폐기를 보존하고 401을 반환한다.
- 웹 logout은 유효 Session이면 기존 단일 Session을 revoke한다. unknown·expired·revoked·누락
  Cookie도 최종 로그아웃 상태로 수렴하도록 Cookie를 삭제하고 204를 반환한다.

### OpenAPI와 Client

- 웹 login·refresh 응답 schema에서 Refresh Token 필드를 제외했다.
- 웹 refresh·logout에는 Refresh Token request body가 없으며 CSRF Header는 required로 표현했다.
- `Set-Cookie`를 JavaScript가 읽는 응답 모델로 노출하지 않았다.
- OpenAPI SSOT에서 TypeScript Client를 재생성했고 API Client, 웹과 모바일 typecheck가 통과했다.

## 테스트 증거

- 기존 signup·login·refresh·logout·me 회귀와 Refresh family 동시성 검증을 포함했다.
- CSRF 초기화, CSRF 없는 세 변경 요청의 공통 403, 로그인 Access-only JSON과 Cookie 속성을 검증했다.
- Cookie 기반 refresh rotation, 재사용 family 폐기, 다른 family 격리를 실제 MySQL에서 검증했다.
- logout의 유효·unknown·expired·revoked·누락 Cookie에 대한 204와 Cookie 삭제를 검증했다.
- localhost credential CORS 허용, `127.0.0.1` 거부, wildcard 금지와 운영 Secure Cookie를 검증했다.
- 웹 응답에 `JSESSIONID`가 없고 알 수 없는 웹 인증 prefix가 보호되는지 검증했다.

## 독립 검토

- Backend/Security: 최초 MEDIUM finding인 웹 인증 prefix 전체 `permitAll` 위험을 exact Endpoint 허용과
  나머지 deny로 보정했다. Controller의 domain exception 직접 의존도 Application Service로 이동해
  계층 Convention을 회복했고 최종 재검토에서 HIGH·MEDIUM finding이 없었다.
- QA: CSRF, Cookie, logout 멱등성, CORS, OpenAPI와 세션 비생성 테스트 범위를 검토했고
  HIGH·MEDIUM finding이 없었다.
- 리뷰어는 파일을 수정하거나 테스트·Gate를 실행하지 않고 코드와 기존 증거만 검토했다.

## Migration

- DB와 Refresh Session schema를 변경하지 않았으며 신규 Flyway migration은 없다.

## 남은 위험과 후속 계약

- M31-16B1은 웹 요청에 `credentials: "include"`를 적용하고 Access Token을 React 메모리에만
  보관하며 login·signup·logout·`/me`와 보호 Route를 연결해야 한다.
- M31-16B2는 시작 시 Cookie refresh를 통한 세션 복구, Access Token 만료 처리,
  single-flight refresh, 동시 401와 브라우저 인증 E2E를 구현해야 한다.
- 브라우저 Origin은 `localhost`로 통일해야 한다. 일부 내부 테스트·서버 bind의 `127.0.0.1` 사용은
  브라우저 CORS Origin 계약이 아니며, 후속 웹 연결에서 혼용하지 않아야 한다.
- 운영은 React와 `/api/**`를 같은 Origin으로 서비스한다는 전제다. cross-site 배포가 필요해지면
  `SameSite=None`을 임의 적용하지 말고 Cookie·CSRF·CORS 정책을 다시 결정해야 한다.
- XSS 신규 구현은 제외했다. M31-16B1에서 서버 문자열을 일반 React text rendering으로 출력하고
  `dangerouslySetInnerHTML`을 사용하지 않는 규칙을 적용해야 한다.
