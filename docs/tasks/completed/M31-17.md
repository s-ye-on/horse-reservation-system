## Auth final contract

- Access Token은 웹 login·refresh JSON 응답으로 전달하며
  `web-access-token-memory.ts`의 모듈 메모리에만 저장한다.
- generated Client의 `accessToken: () => getWebAccessToken()`이 요청마다 최신 Token을 읽는다.
  같은 Client의 A1 요청, A2 교체 요청, clear 이후 Bearer 미사용 회귀가 통과했다.
- Refresh Token은 `HORSE_REFRESH_TOKEN` host-only HttpOnly Cookie로만 전달한다.
  `SameSite=Lax`, `Path=/api/auth/web`, Refresh TTL과 같은 Max-Age를 사용하고
  local은 `Secure=false`, `prod`는 `Secure=true`다.
- `XSRF-TOKEN` Cookie와 `X-XSRF-TOKEN` Header로 web login·refresh·logout을 보호한다.
  CSRF 실패는 공통 JSON `ErrorResponse` 403이다.
- web auth와 일반 API SecurityFilterChain은 모두 `STATELESS`이며 `JSESSIONID`를 생성하지 않는다.
- credential CORS는 `http://localhost:5173`과 외부 `WEB_ALLOWED_ORIGINS` allowlist만 허용하고
  wildcard를 거부한다.
- Refresh Token 회전과 ROTATED 재사용 시 동일 family ACTIVE Session 폐기, 다른 family 격리,
  단일 Session logout 계약이 현재 MySQL 통합 테스트에서 유지됐다.
- 앱 시작 restore는 CSRF 준비, Cookie refresh, `/me`, Role 복구 순서로 동작한다.
- 동일 앱 컨텍스트의 refresh는 single-flight이며 동시 401은 최신 Bearer로 각 요청을 최대 한 번 재시도한다.
- logout·login과 늦은 restore/refresh 결과는 operation version으로 무효화한다.

## Accepted residual risks

- single-flight는 한 JavaScript app context에만 적용된다. 여러 탭이 같은 Refresh Cookie를 동시에
  회전하면 보안 우선 `FAMILY_REVOCATION`으로 재로그인이 필요할 수 있다. 권한 상승이나 Session 유지가
  아니라 가용성·UX 저하이며 첫 배포 blocker로 보지 않는다. Web Locks/BroadcastChannel은 후속 결정이다.
- rate limiting, 자동 계정 잠금, 비밀번호 재설정은 인증 기반의 명시적 후속 범위다.
- 같은 Refresh family의 parent·child `familyId` 동일성은 DB가 직접 강제하지 않고 Application factory와
  MySQL 통합 테스트가 보호한다.
- 운영 인프라와 backup·restore 실증은 아직 수행하지 않았다.

## Final decision

현재 상태에서 Production Deployment 준비 단계로 넘기는 것을 막는 애플리케이션 blocker는 없다.
다만 실제 운영 배포는 아래 환경·인프라 조건과 dependency 재검증을 완료한 뒤 진행해야 한다.

## Production handoff

1. 운영 compute와 MySQL을 선택하고 `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 외부 주입한다.
2. `SPRING_PROFILES_ACTIVE=prod`와 안전한 외부 `JWT_SECRET`을 함께 주입한다.
3. 최초 관리자 생성 시에만 `bootstrap-admin`과 외부 자격 증명을 사용한 뒤 비활성화한다.
4. 실제 domain·DNS·HTTPS/TLS와 reverse proxy를 구성하고 React와 `/api/**`의 same-origin을 우선한다.
5. cross-origin이면 정확한 `WEB_ALLOWED_ORIGINS`만 주입하고 production `Secure` Cookie를 실브라우저에서 확인한다.
6. production artifact serving, Flyway migration 절차, `/actuator/health` health check를 연결한다.
7. application/container 로그 수집, DB backup·restore 절차와 최초 production smoke test를 준비한다.
8. dependency lockfile을 지원 버전으로 갱신한 뒤 audit·build·실제 인증 및 핵심 업무 E2E를 재실행한다.

AWS resource, 운영 DB, DNS, HTTPS와 배포 자체는 M31-17에서 생성하지 않았다.
