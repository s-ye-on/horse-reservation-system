## Completion Evidence

- PM과 Architecture 독립 검토로 R01을 `end_time`, `source=MANUAL`, read-only preflight와
  기존 마감 API 회귀로 제한하고 마감 원인 모델은 R02로 분리했다.
- V16은 V15까지의 데이터에 NULL·비정상 시작 시각, 자정 도달·초과, 계산 불가와 동일
  회원 활성 예약 구간 overlap이 있으면 컬럼 추가 전에 중단한다.
- 운영 사전 점검은 각 문제의 유형, 테이블·ID, 날짜·시작·계산 종료 시각, 충돌 예약 ID와
  유형별·전체 건수를 출력하며 SELECT만 실행한다.
- 기존 TimeSlot과 Reservation을 45분 종료 시각으로 backfill하고 기존 TimeSlot을
  `MANUAL`로 이관했다. 신규 도메인 생성과 예약 변경도 같은 불변식을 유지한다.
- 기존 `is_closed` mutable 쓰기와 관리자 PATCH는 R01에서 유지한다. R02에서 독립 마감
  원인을 쓰기 SSOT로 추가한 뒤 generated `is_closed`를 우선 적용하되 JPA 재조회와 API
  응답 계약이 불안정하면 mutable+CHECK로 전환한다.
- V15 `uk_reservations_active_member_slot`의 네 컬럼 exact-start 제약은 변경하지 않았다.
- Template 정원은 신규 occurrence에만 복사하고 기존 수동 보정과 활성 예약보다 작은
  자동 정원 축소를 금지하는 R04·R06 입력을 SSOT에 기록했다.

## 남은 위험

- `end_time`은 단계적 이관을 위해 R01 DB에서는 nullable이다. 기존 행과 애플리케이션
  신규 쓰기는 값이 있지만 최종 NOT NULL은 R02 migration에서 적용해야 한다.
- 여러 마감 원인의 generated `is_closed`와 JPA 매핑 변경은 R02에서 migration 계약과
  기존 PATCH 회귀를 다시 검증해야 한다.
- 서로 다른 시작 시각의 overlap은 이번 migration에서 기존 데이터만 차단한다. 신규
  Command 동시성 불변식과 인덱스는 M31-R08이 소유한다.
- MySQL 다단계 DDL은 단일 트랜잭션 rollback을 보장하지 않으므로 배포 전에 읽기 전용
  preflight를 hard gate로 먼저 실행해야 한다.

## 중단 조건

- preflight가 실제 운영 DB의 문제 데이터를 발견한다.
- 기존 데이터를 자동 수정·삭제·병합해야 migration을 계속할 수 있다.
- V1~V15 수정이 필요하다.
- 독립 마감 원인이나 Template·휴일 모델을 조기 구현해야 한다.
- generated와 mutable+CHECK 비교 결과가 R02 정책 변경 없이는 안전하지 않다.
- 같은 원인의 검증 실패가 세 번 반복된다.
