# M34-05 Completion Evidence

## 상태

`DONE`

## 구현 계약

- `DELETE /api/admin/schedule-templates/{templateId}`는 Template row를 물리 삭제하지 않고
  기존 `active=false` 전이와 config version 동기화를 시작한다. 미래 TEMPLATE 슬롯은
  `templateInactiveClosed=true`로 닫히고 새 occurrence 생성이 중단된다.
- 삭제 Command는 기존 Reservation 상태, 쿠폰, 결제, 과거 TimeSlot과 감사 이력을 변경하지
  않는다. 미래 점유 Reservation은 M34-02의 Template별 read model에서 계속 조회된다.
- `POST /api/admin/schedule-templates`가 동일 `(dayOfWeek, startTime)`의 inactive Template을
  발견하면 새 row를 만들지 않는다. 기존 ID에 현재 입력 설정을 적용하고 `active=true`로
  전환한 뒤 동일한 versioned synchronization을 시작한다.
- active 동일 key는 기존 `SCHEDULE_TEMPLATE_ALREADY_EXISTS`로 거부한다. inactive 동일 key
  재운영은 M34-04의 전체·원형·RidingClass별 점유 하한 사전 검사를 그대로 사용하며, 충돌
  하나라도 있으면 Template 변경·감사·SYNCING 진입 전체를 롤백한다.
- 삭제와 재운영은 기존 감사 구조에 각각 `DELETED`, `RESUMED` action과 actor, reason,
  이전·이후 상태, pending config version을 남긴다.
- 재운영 동기화는 `templateInactiveClosed`만 해제한다. 관리자 마감과 정기 휴일 등 독립
  closure, 개별 capacity override, MANUAL 슬롯과 과거 occurrence는 보존한다.

관계없는 생성 worker에 의존하지 않도록 Template fixture를 직접 준비했고, assertion이나
production 불변식은 완화하지 않았다.

동기화되지 않는다. 이는 backlog에 이미 배정된 M34-06의 명시적 책임이며, 이번 Gate에서
`api:check`를 PASS로 가장하거나 generated 산출물을 수동 변경하지 않았다. 이 유예는 해당
계약 차이에만 적용하며 다른 실패를 허용하는 일반 예외가 아니다.
