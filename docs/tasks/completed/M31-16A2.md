# M31-16A2: Refresh Token Family 재사용 폐기

## 상태

`DONE`

## 목표

이미 `ROTATED`된 Refresh Token이 다시 제출되면 동일 token family의 모든 `ACTIVE`
Refresh Session을 원자적으로 `REVOKED` 처리하고 기존 공통 401 계약을 유지한다.

## 담당

`backend | db | security | qa | docs`

## 선행 작업

- M31-16A

## 제외 범위

- DB schema와 기존 Flyway migration 변경
- 웹 로그인·회원가입, 자동 Refresh와 Token 저장 방식
- 전체 기기 logout과 일반 logout의 family-wide 변경
- M31-16B1·B2, M31-17 및 M32 이후 작업
- 관련 없는 인증·회원 리팩터링

## 완료 조건

- [x] 정상 회전은 같은 family와 parent chain을 유지한다.
- [x] `ROTATED` Token 재사용은 동일 family의 모든 `ACTIVE` Session을 `REVOKED` 처리하고 401을 반환한다.
- [x] 알 수 없음·만료·`REVOKED` Token은 family 폐기를 실행하지 않는다.
- [x] 다른 로그인 family와 일반 logout의 기존 단일 Session 계약을 유지한다.
- [x] 동일 ACTIVE Token 동시 요청은 성공 1건·401 1건이며 생성된 successor도 폐기된다.
- [x] 관련 MySQL 통합·동시성 테스트와 최종 검증 명령이 모두 성공한다.

## 구현 증거

### 상태 전이와 트랜잭션

- 정상 회전은 기존 token hash 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 `A: ACTIVE -> ROTATED`,
  `B: ACTIVE` 생성과 같은 `familyId`·parent chain을 유지한다.
- 제출된 Session이 이미 `ROTATED`이면 같은 트랜잭션에서 동일 family의 모든 `ACTIVE` 행을
  ID 오름차순으로 `PESSIMISTIC_WRITE` 잠금하고 Entity의 `revoke()`로 `REVOKED` 처리한다.
- family 폐기 뒤 기존 401을 반환하면서 변경이 롤백되지 않도록 내부
  `RefreshTokenReuseDetectedException`에만 `noRollbackFor`를 적용했다. 다른 Auth 예외와 DB 예외의
  rollback 계약은 바꾸지 않았다.
- 외부 응답은 계속 `AUTH_INVALID_REFRESH_TOKEN` 401이며 raw Token, hash와 Session ID를 포함하지 않는다.

### Family 격리와 logout

- Repository 조건은 `familyId + ACTIVE`로 한정하며 기존 V35의 `(family_id, id)` 인덱스를 사용한다.
- 서로 다른 로그인은 별도 `familyId`를 가지므로 재사용 family 폐기가 다른 로그인·기기에 전파되지 않는다.
- unknown·expired·이미 `REVOKED`된 Token과 차단 계정의 refresh는 기존 401만 반환하고 family를 폐기하지 않는다.
- 일반 logout은 제출된 Session 하나만 멱등 폐기하며 같은 family의 방어적 sibling이나 다른 family를 건드리지 않는다.
- V35의 parent FK와 `UNIQUE(parent_session_id)`는 유지했다. parent·child의 동일 `familyId`는 DB가
  직접 강제하지 않고 `createSuccessor()`와 통합 테스트가 보호하는 잔여 애플리케이션 불변식이다.

## 테스트 증거

- 정상 `A -> B -> C` 회전과 family·parent chain 및 최종 상태를 검증한다.
- `A -> B` 후 A 재사용 401, B 재사용 401, 반복 A 재사용의 멱등성을 검증한다.
- 같은 family에 여러 ACTIVE 행을 둔 방어적 fixture도 모두 REVOKED 되는지 검증한다.
- 다른 로그인 family, unknown Token, expired Token, 차단 계정과 logout의 비영향을 검증한다.
- 같은 A의 실제 MySQL 동시 refresh는 성공 1건·401 1건이고 successor가 REVOKED 됨을 검증한다.
- API 401 body의 code·빈 details와 raw Token·hash·Session ID 비노출을 검증한다.

## 독립 검토

- Backend/Security: 전용 `noRollbackFor`, 공통 401, 비노출과 계정·logout 회귀 검토 후 HIGH·MEDIUM 없음.
- DB: V35 재사용, family ACTIVE ID 순 잠금, 기존 인덱스와 다른 family 격리 검토 후 HIGH·MEDIUM 없음.
- QA: 최초 MEDIUM이었던 API 오류 body 계약과 LOW였던 REVOKED logout family 비영향 테스트를
  보강하고 재검토하여 HIGH·MEDIUM 없음.
- 리뷰어는 사용자 지시대로 테스트와 Gate를 실행하지 않고 코드와 기존 집중 테스트 증거만 검토했다.

## 남은 위험

- 서버는 탈취 재사용과 정상적인 중복 네트워크 refresh를 구분할 수 없다. 같은 A의 동시 요청도
  successor를 폐기하므로 사용자는 다시 로그인해야 한다.
- grace period는 도입하지 않았다. M31-16B2에서 클라이언트 single-flight refresh로 정상 중복을 막아야 한다.
- parent와 child의 동일 `familyId`는 DB CHECK/FK로 강제되지 않는다. 현재는 애플리케이션 팩토리와
  MySQL 통합 테스트가 불변식을 보호한다.
