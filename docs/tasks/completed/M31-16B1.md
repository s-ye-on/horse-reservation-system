# M31-16B1: 웹 로그인과 메모리 인증 상태

## 상태

`DONE`

## 목표

M31-16B0의 웹 Cookie·CSRF 계약을 React 애플리케이션에 연결하고 Access Token을
메모리에만 보관한 채 회원가입, 로그인, `/me`, 권한 Route와 로그아웃 흐름을 제공한다.

## 담당

`frontend | qa | docs`

## 선행 작업

- M31-16B0

## 제외 범위

- Backend, DB, Flyway, Spring Security와 OpenAPI 변경
- 자동 refresh, 401 retry, single-flight, 시작 시 세션 복구와 다중 탭 조정
- Access·Refresh Token 영구 저장, XSS sanitizer/filter/CSP
- M31-16B2, M31-17 및 관련 없는 UI 리팩터링

## 완료 조건

- [x] 기존 signup 계약으로 가입하고 성공 후 로그인 화면으로 이동한다.
- [x] login 전에 CSRF를 초기화하고 Cookie 값을 Header로 전달한다.
- [x] Access Token은 모듈 메모리에만 저장하고 중앙 API 경계에서 Bearer로 주입한다.
- [x] `/me` 응답을 사용자·권한 SSOT로 사용한다.
- [x] 비로그인·MEMBER·ADMIN Route 경계를 적용한다.
- [x] 웹 logout 204 후 메모리 인증 상태를 제거한다.
- [x] localStorage·sessionStorage와 Refresh Token JavaScript 접근이 없다.
- [x] 새로고침 시 상태 소실을 B1 제한으로 유지하고 B2 기능을 선행하지 않는다.

## 구현 증거

### 회원가입·로그인·로그아웃

- 회원가입 화면은 생성 Client의 `AuthSignupRequest` 필드만 사용하며 성공 시 자동 로그인 없이
  로그인 화면으로 이동한다.
- 로그인은 `GET /api/auth/web/csrf` 후 `XSRF-TOKEN` Cookie 값을
  `X-XSRF-TOKEN` Header로 전달하며 Cookie 요청에는 `credentials: include`를 사용한다.
- 로그인 응답의 Access Token만 비공개 모듈 메모리에 저장하고 `/api/auth/me` 응답으로
  Account와 Role을 구성한다. JWT payload를 권한 SSOT로 사용하지 않는다.
- 로그아웃은 같은 CSRF 계약으로 `POST /api/auth/web/logout`을 호출하고 성공 후 메모리 Token과
  Account를 제거한다. Refresh Cookie 원문을 읽거나 직접 삭제하지 않는다.

### API·Route 경계

- public, Cookie credential, Bearer 설정을 생성 Client의 `Configuration` 확장 지점에서 분리했다.
- 기존 웹 업무 API adapter는 같은 중앙 Bearer 설정을 재사용하며 각 요청에 Header 코드를 복제하지 않는다.
- MEMBER와 ADMIN 보호 Route를 분리하고 미인증 사용자는 로그인으로, 권한이 다른 사용자는
  접근 거부 화면으로 이동한다.
- 로그인 전 접근한 내부 deep link는 query와 hash를 포함해 복귀하며 프로토콜 상대 경로는 거부한다.

### 저장·B2 경계

- Access Token은 React 상태나 브라우저 영구 저장소가 아닌 모듈 메모리에만 존재한다.
- Provider 제거나 전체 문서 새로고침 후 인증 상태가 사라지는 것은 B1의 명시적 임시 계약이다.
- 자동 refresh, 401 retry, single-flight, 앱 시작 세션 복구와 다중 탭 조정은 구현하지 않았다.
- 새 UI는 서버 문자열을 일반 React text rendering으로 출력하며 `dangerouslySetInnerHTML`을 사용하지 않는다.

### E2E 하네스 호환

- 기존 JWT 업무 흐름 E2E는 웹 login·`/me` 경계를 통해 Provider 상태를 구성한 뒤 업무 API에
  기존 테스트 JWT를 전달한다. 실제 Cookie 원문을 JavaScript로 읽지 않는다.
- 인증 후 화면 이동은 전체 reload가 아닌 SPA 내부 이동을 사용하여 B1의 메모리 저장 계약과 일치시켰다.
- 브라우저 개발 Origin은 `localhost`로 통일했고 Vite proxy는 격리된 E2E backend 주소를 지원한다.
- 늦은 시간 실행 시 이미 시작한 수업을 대상으로 삼던 정책 fixture를 현재 시각에도 유효한
  마감 후 미래 수업으로 보정했다.

## 테스트 증거

- auth API·Provider·화면·Route 테스트 18개가 CSRF, credential, 메모리 Token, `/me`,
  권한 경계, 로그아웃과 deep-link 복귀를 검증한다.
- 전체 웹 테스트 23개 파일 197개가 성공했다.
- 기존 핵심 Playwright E2E 15개가 새 인증 경계를 거쳐 성공했다.
- 정적 검사에서 production auth/API 코드의 localStorage, sessionStorage, IndexedDB,
  자동 refresh와 위험한 HTML 삽입 사용이 없음을 확인했다.

## 독립 검토

- Frontend: 최초 MEDIUM finding인 로그인 후 deep-link 미복귀를 내부 경로 복귀와 회귀 테스트로
  보정했다. 재검토에서 HIGH·MEDIUM finding이 없었다.
- QA: Provider 재생성 시 상태 소실과 401 자동 복구 부재는 각각 확정된 B1 임시 계약과 B2 범위로
  재분류했다. 최종 HIGH·MEDIUM finding이 없었다.
- 두 검토자는 파일 수정·테스트 실행·하위 에이전트 생성·commit을 수행하지 않았다.

## Backend·Migration·Client

- Backend와 DB/Flyway를 변경하지 않았고 신규 migration은 없다.
- OpenAPI와 생성 TypeScript Client를 변경하거나 수동 편집하지 않았다.

## 남은 위험과 후속 계약

- M31-16B2는 앱 시작 시 Cookie refresh, 새로고침 후 세션 복구, Access Token 만료 처리,
  single-flight refresh, 동시 401 제어, 실패 시 전역 인증 만료와 브라우저 인증 E2E를 구현해야 한다.
- B1에서는 Access Token 만료 후 Account 표시와 업무 API 401이 일시적으로 불일치할 수 있다.
  영구 저장이나 임시 retry로 우회하지 않고 B2에서 일관되게 해결한다.
- 다중 탭 refresh coordination도 B2 이후 별도 범위다.
- production bundle의 500KB 초과 경고는 기존 구조적 성능 후속 항목이며 B1 기능 범위에서
  임의 code splitting을 추가하지 않았다.
