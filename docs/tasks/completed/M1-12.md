# M1-12: 쿠폰 없는 입금대기 예약 신청 API

`DONE`

- 쿠폰 임시 점유와 쿠폰 예약 신청

## 완료 조건

- [x] 유효한 클래스 일치 쿠폰이 없을 때만 `single_payment`, `pending_payment` 예약과 신청 시각 기준 2시간의 `payment_due_at`을 만든다.
- [x] 예약 생성과 정원 점유가 한 트랜잭션에서 처리되고 경쟁 요청이 전체·원형·클래스 정원을 넘지 않는다.
- [x] 응답에 상태, 결제원, `payment_due_at`을 포함하며 쿠폰이 있는 요청과 권한·입력 오류를 검증한다.
- [x] 검증 명령이 모두 종료 코드 0으로 성공한다.

## 중단 조건

- 쿠폰 부재 판정과 예약 생성 사이 경쟁을 같은 트랜잭션에서 제어할 수 없다.
- `Asia/Seoul` 기준 신청 시각과 2시간 경계를 고정 Clock으로 검증할 수 없다.
- 정원 점유 실패 뒤 입금대기 예약이 남거나 부분 커밋될 가능성이 있다.
- 외부 결제 상태나 새 결제 스키마가 없으면 구현할 수 있는 요구로 해석된다.
- 허용 범위 밖의 스키마·인증·프론트엔드 변경이 필요하다.

## Completion Evidence

- 서울 시간대 `Clock`을 주입해 신청 시각과 정확히 2시간 뒤의 `payment_due_at`을 같은 트랜잭션에서 생성한다.
- 잠긴 TimeSlot에서 유효한 클래스 일치 쿠폰을 먼저 조회하고, 없을 때만 `single_payment` 예약으로 분기한다.
- 쿠폰이 있으면 M1-11의 `pending_admin_approval`과 임시 점유 경로를 유지한다.
- 경쟁 입금대기 요청이 Reservation 기반 전체·원형·클래스 정원을 초과하지 않음을 MySQL API 테스트로 확인했다.
- `backend/conventions/review.md` 기준으로 DTO 경계, Clock 주입, 트랜잭션·잠금, 예외·테스트 규칙을 점검했다.
