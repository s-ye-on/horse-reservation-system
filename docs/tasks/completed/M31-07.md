## Completion Evidence

- 수업 완료는 Reservation을 잠근 뒤 Coupon 사용과 감사 로그를 먼저 확정하고 Member를
  잠가 `Reservation -> Coupon -> Member` 순서를 사용한다. 완료·노쇼 경쟁에서 상태,
  Coupon 수량, 기승 횟수와 감사 효과는 첫 Command에만 한 번 반영된다.
- TimeSlot 정원 변경과 삭제는 비잠금 날짜 snapshot 뒤
  `Config SHARE -> ScheduleDate FOR UPDATE -> TimeSlot FOR UPDATE` 순서로 잠근다.
  삭제 이력 검사는 기존 `idx_reservations_occupancy`를 사용하는 `FOR UPDATE` 현재 읽기로
  최신 committed Reservation을 재검증한다.
- application 계층의 프록시 가능한 메서드 수준 쓰기 트랜잭션은 접근 제한자와 관계없이
  재시도 경계에 포함한다. 이미 열린 외부 트랜잭션과 read-only 트랜잭션은 제외한다.
- 재시도는 SQLException chain에서 MySQL error code `1213`과 SQLState `40001`이 함께
  확인될 때만 최초 실행 포함 최대 3회 수행한다. 매 시도는 새 transaction과 Persistence
  Context이며 1205 lock wait timeout과 업무 예외는 재시도하지 않는다.
- `DeadlockRetryIntegrationTest`는 실제 InnoDB deadlock, package-private transaction
  boundary, 소진 실패, 1205와 업무 예외를 검증한다.
  `AdminTimeSlotScheduleDateLockIntegrationTest`와
  `TimeSlotDeletionConcurrencyIntegrationTest`는 날짜 전환과 정원 변경·삭제 경쟁을
  검증한다.
- 기존 migration과 Repository 인덱스는 변경하지 않았다.
- `backend/conventions/review.md` 기준으로 Controller/DTO/Domain/Exception 경계를
  변경하지 않았고, 테스트 메서드 한글 규칙과 Convention Gate를 확인했다.
- 독립 Architecture 재검토와 DB 검토는 모두 `GO`이며 HIGH, MEDIUM, LOW finding이
  남지 않았다.

## 남은 위험

- 재시도는 Spring AOP proxy를 통과하는 application 메서드 수준 트랜잭션에만 적용된다.
  self-invocation 또는 프록시되지 않는 private 메서드의 `@Transactional`은 기존 Spring
  제약대로 독립 transaction boundary가 아니며 재시도 대상도 아니다.
- 데이터 분포에 따라 InnoDB의 실제 잠금 범위는 달라질 수 있으므로 변경되는 핵심 SQL은
  M31 lock matrix와 EXPLAIN 검증을 계속 함께 갱신한다.

## 중단 조건

- 1213 외 오류를 재시도해야 검증이 통과한다.
- retry가 이미 열린 외부 트랜잭션 안에서 `REQUIRES_NEW`를 반복해야 한다.
- Command 전체가 아니라 Repository 일부만 재시도해야 한다.
- 기존 제품 정책, migration 또는 Repository 인덱스 변경이 필요하다.
- 재시도 뒤 Coupon·Reservation·Member·감사 효과를 exactly-once로 보장할 수 없다.
- 독립 Architecture·DB 검토에 HIGH 또는 MEDIUM blocker가 남는다.
