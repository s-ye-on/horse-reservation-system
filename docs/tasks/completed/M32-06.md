# M32-06 Completion Evidence

## 목표

일반 클래스 catalog에 구보초보와 구보를 추가하고, ADR-019의 실제 일반 기승,
progression baseline, Special Approval 인정분과 Promotion Hold 계약을 Backend와 DB의
결정적인 상태 및 계산으로 구현한다.

## 구현

- 일반 progression
  - 기존 `general_ride_count`를 실제 완료 일반 기승의 단일 원천으로 유지한다.
  - `GeneralRidingGrade`가 threshold를 단일 원천으로 보유하며 enum ordinal이 아니라
    명시적 threshold로 progression class와 상·하위 관계를 판정한다.
  - 구보초보 70회와 구보 100회 경계를 일반 예약 자격과 class catalog에 추가한다.
- progression baseline
  - 시작 클래스 threshold `T`와 설정 당시 실제 일반 기승 `B`를 snapshot으로 보존한다.
  - 파생 인정분 `max(0, T - B)`만 progression에 반영하고 실제 기승 횟수는 변경하지 않는다.
  - 최초 baseline이 기존 회원의 write-once 관리 시작 시각을 설정하며 이후 변경·해제는
    그 시각을 다시 쓰지 않는다. 최초 baseline에서는 초기화 감사와 baseline 설정 감사를
    같은 transaction에 순서대로 남긴다.
- Special Approval
  - 승인 직전 progression `P`가 대마장 속보 threshold `S`보다 낮을 때만
    `max(0, S - P)`를 영속 인정분에 추가한다.
  - 승인 해제와 재승인에서 인정분을 회수하거나 중복하지 않으며 특수 수업 완료는 기존처럼
    일반 기승에 포함하지 않는다.
  - 잘못된 인정분은 모든 특수 승인을 해제한 뒤 별도 관리자 Command로 하향 교정한다.
- Promotion Hold
  - progression은 계속 누적하고 effective class만 명시적 일반 클래스 상한으로 제한한다.
  - Special Approval과 상호 배타다. 이후 baseline 또는 인정분 교정으로 progression이 hold보다
    낮아져도 hold 자체는 보존하고 effective class를 올리지 않는다.
- 감사와 동시성
  - 신규 회원 초기화, baseline 설정·변경·해제, 특수 승인과 인정분 교정,
    hold 설정·변경·해제를 전후 snapshot, 관리자, 시각과 필수 사유로 기록한다.
  - 관리자 Command는 회원 행을 비관적 잠금한 동일 transaction에서 상태와 감사를 변경한다.
- catalog 전파
  - Reservation class 제약, `TimeSlotCapacity`, `RegularScheduleTemplate`, materialized
    TimeSlot 정원 JSON과 기존 관리자/회원 Web의 클래스 표시 및 정원 입력에 두 클래스를 추가한다.
  - 기존 정원 JSON은 migration에서 두 새 key를 0으로 보강하여 기존 운영 정원을 임의로 열지 않는다.
  - M32-08의 baseline/hold/횟수 보정 관리 UI와 M32-09의 OpenAPI 생성 Client 동기화는
    선행하지 않는다. 기존 특수 승인 UI에는 새 필수 감사 사유 입력만 연결한다.

## DB

- `V38__add_member_class_progression.sql`
  - 회원 progression 관리 시작, baseline snapshot, Special Approval 인정분과 Promotion Hold 상태
  - append-only 회원 클래스 progression 감사 원장
  - baseline shape·threshold, Special Approval/Hold 상호 배타 DB 제약
  - 기존 특수 승인 회원의 대마장 속보 부족분 전환과 migration 감사
  - 기존 특수 승인 회원의 관리 시작 경계는 회원 가입 시각으로 소급하지 않고 V38 전환 시각으로 설정
  - Reservation 및 정원 JSON catalog의 구보초보·구보 전파

## 검증 시나리오

- baseline 없음, 최초 설정, 변경, 해제와 write-once 관리 시작 경계
- 실제 일반 기승 증가와 baseline 인정분의 분리
- Special Approval 부족분, 이미 높은 progression, 두 번째 승인, 해제와 재승인
- 인정분 하향 교정과 Special Approval/Hold 상호 배타
- Hold 중 progression 증가, Hold 해제와 baseline/credit 교정 불변식
- 70회 구보초보와 100회 구보 경계 및 회원 예약 자격
- 구보 클래스 완료는 일반 기승을 1회 증가시키고 특수 클래스 완료는 일반 progression에 미반영
- V37→V38 데이터 보존, 기존 특수 승인 전환, 정원 JSON backfill과 DB 제약
- 관리자 특수 승인 필수 사유와 기존 Web 클래스 catalog 표시
