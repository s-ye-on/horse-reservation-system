## 상태

single-flight refresh, 중앙 401 재시도와 실제 브라우저 인증 회귀를 추가한다.

## 완료 조건

- [x] 같은 generated Client가 요청마다 메모리 Access Token을 동적으로 읽는다.
- [x] 앱 시작 시 CSRF와 Refresh Cookie로 Access Token을 갱신하고 `/me`로 Account·Role을 복구한다.
- [x] 동시 refresh와 동시 401은 앱 컨텍스트에서 하나의 refresh HTTP 요청을 공유한다.
- [x] 보호 API 401은 최신 Bearer로 원 요청을 최대 한 번만 재시도하고 재시도 401은 인증을 종료한다.
- [x] logout이 시작된 뒤 늦게 도착한 refresh는 Token이나 Account를 복구하지 못한다.
- [x] 실제 브라우저에서 login, 401 자동 refresh, full reload 복구와 logout 후 미복구가 성공한다.

## 구현 증거

### 동적 Access Token과 중앙 재시도

- `bearerApiConfiguration`은 `accessToken: () => getWebAccessToken()`을 유지한다. generated runtime은
  API 요청을 만들 때마다 이 함수를 호출하므로 같은 Client 인스턴스가 A1, A2, Token 없음 상태를
  순서대로 반영한다.
- `authenticatedFetch`는 generated `Configuration.fetchApi` 확장점 한 곳에서만 401을 처리한다.
  403과 인증 Endpoint는 refresh 대상이 아니며, 재시도는 전역 fetch를 직접 한 번 호출해 재귀를 막는다.
- 여러 요청이 A1로 401을 받는 동안 첫 요청이 A2를 발급받으면 후속 요청은 요청 당시 Token과 현재
  Token의 차이를 확인해 추가 rotation 없이 A2로 재시도한다.

### 시작 복구와 실패 정책

- `AuthProvider`는 `initializing`, `authenticated`, `unauthenticated`, `restore-error`를 구분한다.
  초기화 중에는 보호 Route를 redirect하지 않고, 성공 시 refresh 응답의 Token과 `/me` 응답으로
  인증 상태를 복원한다.
- Refresh 401은 Token·Account를 제거하고 정상 비로그인 상태가 된다. CSRF 403은 Token을 제거하고
  다음 명시적 시도에서 `/api/auth/web/csrf` 초기화를 강제한다. 자동 CSRF·refresh 반복은 없다.
- network·5xx는 서버 logout이나 Cookie 삭제로 오판하지 않는다. 공개 login·signup 화면을 유지하면서
  비차단 오류와 명시적 재시도 진입점을 제공한다.

### single-flight와 경쟁 제어

- 앱 모듈 단위의 공유 refresh Promise가 성공·실패를 모든 caller와 공유하고 `finally`에서 정리된다.
- 인증 operation version으로 login, logout, startup restore와 자동 refresh의 선후 관계를 검증한다.
  logout 이후 도착한 이전 refresh는 stale 결과로 폐기되어 메모리 Token과 Account를 되살리지 못한다.
- React StrictMode의 Effect 재실행은 Provider의 공유 restore Promise와 refresh single-flight로 실제
  refresh HTTP 요청 한 건과 `/me` 한 건으로 수렴한다.

### 실제 브라우저 인증

- 전용 Playwright 시나리오는 mock 인증 helper를 사용하지 않고 실제 React, Spring Backend와 브라우저
  Cookie로 signup, web login, `/me`, full reload restore, logout을 통과한다.
- 실제 login 이후 `/api/auth/me`의 첫 응답만 401로 제어하고 실제 `/api/auth/web/refresh` 한 번과
  `/me` 초기 요청·재시도 두 번, 최종 로그인 성공을 검증한다.
- Refresh Cookie assertion은 이름, HttpOnly, Path와 SameSite metadata만 사용하며 원문을 읽거나
  출력하지 않는다.

## Backend·Migration·Client

- Backend와 DB/Flyway를 변경하지 않았고 신규 migration은 없다.

## 남은 위험과 M31-17 입력

- single-flight는 하나의 JavaScript 앱 컨텍스트 안에서만 동작한다. 같은 브라우저 프로필의 여러 탭이
  동시에 같은 Refresh Cookie를 회전하면 서버의 보안 우선 `FAMILY_REVOCATION`에 따라 successor까지
  폐기되고 재로그인이 필요할 수 있다. Backend grace period나 family 정책을 약화하지 않았으며,
  browser-native 다중 탭 조정은 별도 정책 결정 후 수행한다.
- production bundle의 500KB 초과 경고는 기존 구조적 성능 후속 항목이다. B2 범위에서 임의 code
  splitting을 추가하지 않았다.
- M31-17은 실제 인증 E2E와 기존 mock 업무 E2E의 책임 분리, 다중 탭 잔여 위험과 B2 전용 Gate를
  Phase A 전체 품질 Matrix에 포함해야 한다.
