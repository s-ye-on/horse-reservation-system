## 동기화 계약

- `GET /api/admin/schedule-templates/{templateId}/future-occupying-reservations`를 OpenAPI와
  generated TypeScript client에 반영했다. 응답은 Template ID, 미래 점유 Reservation 수와
  목록을 제공하며 날짜·시각 format, RidingClass와 점유 ReservationStatus enum을 runtime과
  동일하게 고정한다.
- `DELETE /api/admin/schedule-templates/{templateId}`를 `expectedConfigVersion`과 `reason`이
  필수인 요청 및 `ScheduleTemplateMutationResponse` 응답으로 동기화했다. Hard Delete가 아닌
  향후 운영 종료라는 runtime 의미도 API 설명에 보존했다.
- 동일 key의 inactive Template을 재사용하는 `POST /api/admin/schedule-templates`의 외부 의미를
  문서화했다. 요청·성공 응답 shape은 기존 create 계약을 유지한다.
- create/update의 409는 `code` discriminator를 사용하는
  `ScheduleTemplateMutationConflictResponse`로 명세했다. 설정 version 충돌과 active 동일 key
  중복은 일반 충돌 응답으로, 정원 점유 하한 충돌은 날짜·시각·현재 점유·요청 정원을 가진
  구조화된 응답으로 타입 안전하게 구분한다.
- generated client는 미래 점유 Reservation 조회와 Template 삭제 메서드, 요청·응답 DTO,
  RidingClass/ReservationStatus enum, capacity conflict details와 discriminator union을 제공한다.

## 독립 검토

- 첫 검토는 capacity 충돌 상세가 설명 문자열과 자유 형식 `details`로만 노출되어 Web이 타입
  안전하게 소비할 수 없다는 MEDIUM을 발견했다. 구조화된 details/error DTO와 schema 검증으로
  해결했다.
- 재검토는 create/update의 모든 409를 capacity 오류로 좁힌 문제와 범용 오류가 capacity 오류도
  포함해 `oneOf`가 배타적이지 않은 문제를 각각 MEDIUM으로 발견했다. 실제 runtime code enum을
  분리하고 discriminator mapping을 추가하여 generated parser도 code별 DTO를 선택하게 했다.
- 최종 읽기 전용 reviewer는 runtime, OpenAPI, generated client의 분기와 타입이 일치하고
  CRITICAL/HIGH/MEDIUM/LOW finding이 없음을 확인해 `PASS`했다.
