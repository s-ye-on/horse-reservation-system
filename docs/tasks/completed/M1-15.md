# M1-15: 입금대기 자동 만료 job

## 상태

`DONE`

## 재개 결정

- M1에는 `ROLE_SYSTEM`을 도입하지 않는다.
- Spring `@Scheduled`가 `PendingPaymentExpiryService`를 직접 호출한다.
- 관리자는 `POST /api/admin/jobs/expire-pending-payments`로 같은 Service를 수동 실행한다.
- `payment_expired`는 복구 가능한 운영 자동화 상태로 유지한다.
- 상세 근거는 [ADR 006](../../architecture/adr-006-pending-payment-expiry-execution.md)을 따른다.

## 목표

결제 마감이 지난 입금대기 예약을 멱등하게 만료하고 점유 정원을 반환한다.

- 만료 예약 복구와 관리자 입금 확인

## 완료 조건

- [x] `payment_due_at`이 현재 시각 이하인 `pending_payment`만 `payment_expired`로 전이하고 정원을 반환한다.
- [x] `Asia/Seoul` 2시간 경계, 확정과 만료의 경쟁, 반복 실행을 자동 테스트하며 정원을 한 번만 반환한다.
- [x] Spring Scheduler와 ADMIN 수동 실행 API가 같은 Service를 사용하고 쿠폰 예약과 다른 상태는 변경하지 않는다.
- [x] 검증 명령이 모두 종료 코드 0으로 성공한다.

## Completion Evidence

- `PendingPaymentExpiryService`가 만료 대상 잠금 조회, 상태 전이, 트랜잭션과 멱등성을 단독 소유한다.
- Spring Scheduler와 `POST /api/admin/jobs/expire-pending-payments`가 같은 Service를 호출하며 수동 API는 ADMIN만 접근한다.
- `payment_due_at <= now` 경계와 쿠폰 승인대기·확정 예약 비변경을 고정 `Asia/Seoul` Clock으로 검증했다.
- 동시·반복 실행과 관리자 확정 경쟁에서 예약 버전이 한 번만 증가하고 정원 집계에서 제외됨을 MySQL로 확인했다.
- ADR 006에 `ROLE_SYSTEM` 유보와 `payment_expired` 복구 가능 운영 상태 결정을 기록했다.
- `backend/conventions/review.md` 기준 계층 경계, Entity 상태 변경, 예외 계층, 테스트 범위를 자기 점검했다.

## 중단 조건

- 관리자 수동 실행 API를 기존 `ROLE_ADMIN` 경계로 제한할 수 없다.
- 만료 처리와 정원 반환을 한 command 트랜잭션으로 묶을 수 없다.
- 여러 인스턴스의 동시 실행에서 같은 예약의 정원을 중복 반환할 가능성을 차단할 수 없다.
- 승인대기 쿠폰 예약도 시간 만료해야 한다는 요구가 발견된다.
- 고정 Clock으로 2시간 경계와 재실행을 자동 검증할 수 없다.
