## 완료 조건

- [x] 대소문자 구분 `reservations.status`에서 V30이 잘못 완료한 migration closure를 V32가
  `IN_PROGRESS`로 복구하고 완료 주체·시각을 제거한다.
- [x] 활성 상태는 DB generated `active_slot_guard`를 SSOT로 사용하고 누락 Impact를
  중복 없이 생성한다.
- [x] 다른 `IN_PROGRESS` closure가 있는 TimeSlot에는 두 번째 활성 closure를 만들지
  않는다.
- [x] 활성 예약이 없는 완료 이력과 정상 이관 결과는 변경하지 않는다.
- [x] V29→V31→V32 실제 upgrade, 빈 스키마 V1→V32, Flyway validate가 통과한다.
- [x] 기존 V1~V31 migration이 수정되지 않는다.
- [x] 모든 검증 명령이 종료 코드 0으로 성공한다.

## 완료 증거

- V32는 `started_by`와 `completed_by`가 `migration:v30`인 완료 이력만 보정하고,
  다른 `IN_PROGRESS` closure가 있으면 기존 이력을 다시 열지 않는다.
- 활성 예약 판정은 상태 문자열을 재복제하지 않고 V15의 generated
  `active_slot_guard = 1`을 사용한다. 누락 Impact는 기존 membership을 LEFT JOIN으로
  제외하고 예약 ID 순으로 생성한다.
- `reservations.status`가 case-sensitive인 V29→V31 환경에서 활성 상태 3종이 모두
  잘못 누락되는 현상을 재현한 뒤 V32가 완료 주체·시각을 제거하고 3개 Impact를
  복구함을 검증했다.
- 활성 예약이 없는 완료 이력, 기본 collation 정상 이관, 다른 활성 Closure 존재,
  빈 스키마 V1→V32와 Flyway validate를 실제 MySQL 8.4에서 검증했다.
- verifier는 SQL과 Java Flyway migration 경로를 모두 검사해 기존 V1~V31 변경을
  허용하지 않는다.
- DB·Backend 독립 검토의 활성 상태 범위, 기존 활성 Closure, Java migration 경로,
  `completed_at` assertion finding을 보정한 뒤 HIGH 또는 MEDIUM finding 없이 `GO`를
  받았다.

## 중단 조건

- 기존 V1~V31 migration 수정이 필요하다.
- 보정 대상 closure를 migration 식별 정보만으로 안전하게 한정할 수 없다.
- 기존 운영 이력 또는 활성 closure를 덮어쓸 가능성이 있다.
- Flyway upgrade를 실제 MySQL에서 재현할 수 없다.
- 관련 없는 dirty 파일 수정이 필요하다.
- HIGH 또는 MEDIUM 독립 검토 finding을 G02 범위에서 해결할 수 없다.
- 같은 원인의 검증 실패가 세 번 반복된다.
