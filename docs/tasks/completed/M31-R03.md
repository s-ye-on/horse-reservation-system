## Completion Evidence

### Migration과 데이터 보존

- V25 Java migration이 실행 시점의 ScheduleConfigGuard `activeVersion`을 읽고 기존
  TimeSlot·Reservation의 distinct 수업 날짜를 ScheduleDate로 보존한다.
- Asia/Seoul 기준 오늘부터 `today.plusMonths(3)`까지 양 끝을 포함해 최초 horizon을
  채운다. 실행 날짜에 상대적인 운영 데이터 migration이라는 점은 Task 계약에 따른
  의도된 동작이다.
- 기존 ScheduleDate는 삭제하거나 상태·version을 덮어쓰지 않는다. 새 행만 `NORMAL`과
  실행 시점의 active version으로 생성한다.
- V1~V24 migration은 수정하지 않았고 V25는 ScheduleDate DML만 수행한다.

### 일일 보충과 동시성

- 일일 Scheduler는 `00:05 Asia/Seoul`에 Application Service를 호출하고 주입된 Clock의
  instant를 Asia/Seoul 날짜로 변환한다.
- Application Service는 Config guard를 `FOR SHARE`로 읽은 뒤 ACTIVE일 때만 horizon을
  보충한다. SYNCING 중에는 stale active version 행을 추가하지 않고 R06의 pending
  version 동기화에 맡긴다.
- `uk_schedule_dates_date`가 날짜별 최종 유일성을 보장한다. 동시 실행은
  `INSERT IGNORE`로 duplicate key만 멱등 처리하고 JDBC warning을 검사해 error code
  1062 이외의 경고는 실패시킨다.
- 다음 날 실행은 새 마지막 날짜만 추가하며 과거 ScheduleDate와 기존
  `appliedConfigVersion`을 보존한다.

### 독립 검토

- PM 검토의 Completion Evidence·공통 Gate 누락은 본 문서와 최종 검증 표로 보완했다.
  운영 Scheduler는 다음 날 보충 요구의 실행 진입점으로 R03 범위에 유지했다.
- Architecture 검토의 SYNCING version 위험은 ACTIVE 상태에서만 보충하도록 수정하고
  SYNCING no-op 통합 테스트를 추가했다. Clock Bean과 `@EnableScheduling`이 기존
  reservation 설정에 위치한 결합은 R03에서 이동하지 않고 후속 모듈 정리 위험으로
  기록한다.
- DB 검토의 `INSERT IGNORE` 경고 은폐 위험은 duplicate key warning만 허용하는 명시적
  검사로 보완했다. V25의 실행 날짜 상대성은 최초 3개월 horizon 계약상 의도된
  데이터 초기화이며 스키마 재현성에는 영향을 주지 않는다.

## 남은 위험과 후속 범위

- R04·R05가 guard를 SYNCING으로 전환한 뒤 R06이 배포되지 않은 부분 배포는 horizon
  보충과 설정 반영을 정지시킨다. R04~R06은 이번 연속 Task 루프에서 순차 완료하고 함께
  배포해야 한다.
- R06은 pending version 동기화 시작 전에 horizon 전체가 존재함을 재검증하고 누락
  ScheduleDate가 있으면 pending version 적용 workflow 안에서 보충해야 한다.
- TimeSlot occurrence 생성, Template·정기 휴일 관리와 설정 진행률은 R04~R06 범위다.
- schedules가 사용하는 공용 Clock Bean과 Scheduling 활성화 설정은 현재 기존
  reservations infrastructure에 있다. 동작에는 문제가 없지만 모듈 분리 시 공용 설정
  재배치를 검토한다.

## 중단 조건

- 기존 V1~V24 migration 수정이 필요하다.
- 기존 데이터를 수정·삭제·병합해야 한다.
- TimeSlot occurrence 또는 설정 변경 workflow를 조기 구현해야 한다.
- active version 이외의 초기 적용 version 정책이 필요하다.
- 관련 없는 파일 수정이나 기존 검증 완화가 필요하다.
- 같은 원인의 검증 실패가 세 번 반복된다.
