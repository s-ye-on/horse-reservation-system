# AI 실행 작업 보드

MVP 문서는 backlog다. AI loop는 MVP 문서 전체를 입력으로 사용하지 않는다. 한 번에 backlog 항목 하나를 선택하고 [실행 작업 템플릿](TEMPLATE.md)을 채운 `active/<task-id>.md`만 실행한다.

## 단계

| 단계 | 목표 | 실행 문서 |
|---|---|---|
| [MVP 0](mvp-0.md) | 하네스와 프로젝트 골격 | 작은 기반 작업 |
| [MVP 1](mvp-1.md) | 반응형 웹 예약 운영 | API·정책·화면별 작업 |
| [MVP 2](mvp-2.md) | 변경·취소 자동화 | 정책 분기별 작업 |
| [MVP 3](mvp-3.md) | 관리자 운영 효율화 | 조회·일괄 처리별 작업 |
| [MVP 3.1](mvp-3.1.md) | 운영 안정화 | 시간·동시성·API 계약별 작업 |
| [MVP 3.2](mvp-3.2.md) | 가족 쿠폰과 클래스 | 가족·쿠폰·회원 권한별 작업 |
| [MVP 3.3](mvp-3.3.md) | 관리자 운영 가시성 | 월간 완료 실적·주간 TimeSlot 조회별 작업 |
| [MVP 4](mvp-4.md) | 회원 모바일 앱 | 모바일 화면·흐름별 작업 |

## 작업 크기 상한

실행 작업 하나는 다음을 모두 만족해야 한다.

- 담당 에이전트 1개
- 주요 동작 1개
- DB 마이그레이션, API 유스케이스, UI 화면 중 원칙적으로 1종류
- 완료 조건 최대 4개
- 필수 검증 명령 최대 3개
- 백엔드와 프론트엔드를 동시에 수정하지 않음
- 예상 변경이 넓어지면 작업을 나누고 현재 loop를 중단

## 실행 절차

1. MVP backlog에서 의존성이 끝난 항목 하나를 선택한다.
2. `TEMPLATE.md`를 `active/<task-id>.md`로 복사해 빈 항목을 모두 채운다.
3. `mise tasks --all`로 검증 명령 존재를 확인한다.
4. 허용 범위와 제외 범위를 확인한다.
5. 구현과 테스트를 함께 작성한다.
6. 작업 문서의 검증 명령을 순서대로 실행한다.
7. 명령, 종료 코드, 핵심 출력을 검증 증거에 기록한다.
8. 중단 조건이 없고 모든 검증이 성공한 경우에만 완료 처리한다.

## 하네스 원칙

- 모든 실행 작업은 `mise run verify:<task-id>` 명령을 가져야 한다.
- 명령이 아직 없으면 그 명령을 만드는 선행 작업이 필요하며 현재 작업은 시작하지 않는다.
- 테스트 파일이나 코드가 없어 검증할 수 없다는 것은 성공이 아니라 `BLOCKED`다.
- M0-00만 예외적으로 하네스 자체를 만드는 부트스트랩 작업이다.
- 상세 명령 계약은 [verification-contract.md](verification-contract.md)를 따른다.

## 공통 중단 원칙

정책 충돌, 범위 초과, 데이터 손실 가능성, 인증·권한 모호성, 선행 작업 누락, 재현되지 않는 검증을 발견하면 추측해 구현하지 않는다. 현재 작업을 `BLOCKED`로 기록하고 충돌한 문서와 필요한 결정을 남긴다.

## 아직 필요한 제품 결정

- 회원 가입 방식과 초기 계정 발급 주체
- 실제 배포 환경과 관리자 접근 정책
- 1회 결제 환불을 시스템 상태만 관리할지 외부 결제와 연동할지
- 첫 기승 완료로 만료일이 확정됐을 때 만료일 이후 임시 점유 예약 처리
