# Horse 전체 UI 리디자인 Design Brief

## 1. 문서 목적

Horse는 회원의 수업 예약과 쿠폰 사용, 관리자의 예약·회원·일정·출석 운영을 연결하는 마장 예약 서비스다.

이번 리디자인의 목적은 기존 브랜드를 변경하는 것이 아니라, 초기 예약 프로토타입을 현재 Horse의 실제 기능과 정책에 맞는 전체 서비스 UI로 확장하는 것이다.

- 기존 `horse-reservation.html`의 로고 유지
- Burgundy `#800020` 중심의 브랜드 분위기 유지
- 기존 URL이나 API 수와 화면 수를 1:1로 대응하지 않음
- 회원에게는 간결한 예약 경험, 관리자에게는 밀도 높은 운영 도구 제공
- 반응형 Web이 현재 제공 채널이며 모바일 앱은 MVP 4 예정 범위로 구분

## 2. Design Brief와 제품 정책 SSOT

이 문서는 OpenDesign이 Horse의 전체 UI와 사용자 흐름을 설계하기 위한 **Design Brief**다. 비즈니스 정책을 새로 결정하거나 확정하는 최종 SSOT가 아니다.

예약 가능 기간, 예약 마감 시각, 상태 전이, 쿠폰 점유·차감·반환, 승인, 입금 확인, 변경, 취소, 만료 등 실제 제품 동작은 다음 근거를 우선한다.

1. `docs/product/policies.md`
2. Accepted ADR
3. 현재 Backend와 OpenAPI의 API 계약
4. 해당 계약을 검증하는 production test

이 문서의 숫자, 상태, 시간과 처리 방식은 현재 UI를 설계하기 위한 **현재 시점의 snapshot**이다. 향후 제품 정책이 변경되면 Design Brief가 아니라 제품 정책 SSOT를 기준으로 UI를 다시 정합화한다.

Design Brief와 제품 정책 SSOT가 충돌하면 항상 제품 정책 SSOT를 따른다. OpenDesign은 이 문서의 설명만으로 새로운 비즈니스 규칙을 만들거나 기존 정책을 변경하지 않는다.

## 3. 사용자 역할

| 역할 | 주된 목적 |
|---|---|
| 비로그인 사용자 | 서비스 진입, 로그인, 회원가입 |
| 회원 | 가능한 수업 조회, 예약 신청·변경·취소, 예약 상태와 쿠폰 확인 |
| 관리자 | 예약 승인·입금·출석 처리, 회원·쿠폰 관리, 시간표·휴무 운영, 통계·감사 확인 |

ADMIN 계정은 회원 기승 프로필을 가지지 않는다. 회원 화면과 관리자 화면은 역할별로 명확히 분리한다.

## 4. 공통 UX 원칙

1. **운영 사실 우선**: 잔여석, 예약 상태, 쿠폰 상태를 프론트에서 추론하지 않고 서버 결과를 표시한다.
2. **다음 행동 제시**: 상태명만 보여주지 말고 사용자가 지금 할 수 있는 행동과 막힌 이유를 함께 제공한다.
3. **상태와 경고 분리**: 예약 상태, 승인 지연 경고, 행동 가능 여부를 하나의 배지로 합치지 않는다.
4. **확인 후 실행**: 취소·반려·삭제·휴강·쿠폰 차감 같은 행위는 영향과 사유를 실행 맥락 안에서 확인한다.
5. **실패를 빈 화면으로 위장하지 않음**: 실제 0건, 권한 없음, 마감, 서버 오류를 서로 다른 상태로 표현한다.
6. **사용자 언어 사용**: enum, DTO명, DB 필드명과 내부 lifecycle 용어 대신 역할에 맞는 자연스러운 한국어를 사용한다.
7. **접근성 기본값**: 키보드 탐색, 보이는 포커스, 44px 이상 터치 영역, 색상 외 상태 표식, `aria-live` 피드백을 제공한다.

### 내부 용어와 UI 문구

`SYNCING`, `active`, `pending_admin_approval`, DTO명 같은 내부 용어는 기술 참고와 개발 handoff에는 사용할 수 있지만 실제 UI 카피에 그대로 노출하지 않는다.

예:

- `SYNCING` → “일정 변경 사항을 반영하고 있습니다. 잠시 후 다시 시도해 주세요.”
- `active=false` → “현재 운영하지 않는 정규 시간표”
- `pending_admin_approval` → “관리자 승인대기”
- `payment_expired` → “입금 기한 만료”

운영자는 내부 상태 이름이 아니라 현재 상황, 영향과 다음 행동을 이해할 수 있어야 한다.

## 5. Visual Identity

Visual Identity는 이번 리디자인의 변경 대상이 아니다.

OpenDesign은 다음 요소를 기준으로 정보구조와 화면을 확장해야 하며, 별도의 시각 콘셉트로 교체해서는 안 된다.

- 기존 로고 시각 자산 유지
- Primary brand color인 Burgundy `#800020` 유지
- Off White `#FAFAFA`, White `#FFFFFF`, Near Black `#111111` 중심 톤 유지
- 현재의 차분하고 절제된 브랜드 분위기 유지
- 편집물처럼 명확한 제목 계층과 선·여백 중심 구성 유지
- 성공·주의·위험 색은 보조적인 의미 전달에만 사용

OpenDesign은 다음을 임의로 제안하거나 교체하지 않는다.

- 새로운 로고 또는 심볼
- 새로운 primary brand color
- 기존 분위기와 다른 별도의 visual concept
- Burgundy를 대체하는 gradient나 다색 브랜드 체계
- 과도한 그림자, glassmorphism, 장식용 gradient
- 브랜드와 무관한 illustration 중심 콘셉트

본문은 한국어 가독성이 높은 시스템 또는 CJK 대응 sans-serif를 우선한다. 영문 제목의 serif 분위기는 유지할 수 있지만 한국어 제목 서체는 실제 렌더링 검증 후 확정한다.

카드 중첩을 피하고 기본 radius는 8px 중심으로 통일한다. Dialog 같은 큰 표면만 제한적으로 확장할 수 있다.

**확인 불가**: 실제 서비스의 최종 워드마크 문구가 `Horse`, `Unicorn Stable`, `유니콘승마클럽` 중 어떤 조합인지는 현재 정책에서 확인되지 않았다. 기존 로고 시각 자산은 유지하되 문구 조합은 별도 확정 전까지 임의 변경하지 않는다.

## 6. 회원 정보 구조

### 6.1 회원 홈

한 화면에서 다음을 요약한다.

- 가장 가까운 예약과 현재 상태
- 승인 또는 입금처럼 회원이 확인해야 할 항목
- 사용 가능한 쿠폰 수와 임시 점유 횟수
- `수업 예약`, `내 예약`, `내 쿠폰` 주요 진입점

프로토타입의 예약 현황 요약 구조는 유지하되 실제 서버 데이터만 사용한다.

### 6.2 수업 찾기와 예약

고정 7단계 wizard 대신 다음 세 가지 맥락으로 단순화한다.

1. **수업 찾기**: 예약 가능한 클래스, 날짜, 실제 TimeSlot과 잔여석 선택
2. **신청 확인**: 날짜·시간·클래스·쿠폰 적용 결과 확인
3. **신청 결과**: 승인대기 또는 입금대기 상태와 다음 행동 안내

회원 자격에 맞는 클래스만 제공하며 예약 가능 기간과 마감은 현재 제품 정책과 API 결과를 따른다.

유효 쿠폰은 서버가 자동 선택하고, 없으면 1회 결제 입금대기로 신청한다.

온라인 카드 결제, 임의 가격, 결제수단 선택 화면은 만들지 않는다. 현재 Horse에는 온라인 결제 연동이 없다.

### 6.3 내 예약

- 예정 / 지난 예약 탭
- 예정 예약의 승인대기·입금대기·확정 필터
- 예약별 날짜, 시간, 클래스, 상태, 연결 쿠폰과 행동 가능 여부
- 상세 또는 확장 영역에서 변경·취소 진입
- 변경·취소 전에 서버 preview로 조건과 쿠폰 처리 결과 안내
- 반려 사유와 최종 쿠폰 처리 결과 제공
- 관리자 메모나 내부 책임 코드는 회원에게 노출하지 않음

### 6.4 내 쿠폰

- 일반·마장마술·장애물 쿠폰 구분
- 총 횟수, 잔여, 예약 점유, 현재 사용 가능 횟수
- 첫 사용일, 만료일, 무료 변경권
- 사용·점유·반환·차감·만료 이력
- 가족 쿠폰을 사용한 경우에도 실제 쿠폰과 이력 의미를 왜곡하지 않음

별도 회원 프로필 화면은 현재 route에서 확인되지 않았다. OpenDesign에서 임의로 만들지 않고 확인 불가 항목으로 남긴다.

## 7. 관리자 정보 구조

관리자 메뉴는 API별 화면이 아니라 다음 업무 영역으로 묶는다.

| 업무 영역 | 포함 기능 |
|---|---|
| 운영 홈 | 승인대기·입금대기·만료 건수, 긴급 경고, 오늘 수업과 빠른 진입 |
| 예약 운영 | 예약 검색·상세, 승인·반려·입금 확인·복구, 변경·취소, 관리자 수동 예약 |
| 출석 운영 | 수업별 완료·노쇼와 일괄 처리 |
| 일정 운영 | 주간 운영 캘린더, TimeSlot 정원, 날짜 휴무, 개별 휴강 |
| 정규 설정 | 정규 시간표, 정기 휴일, 동기화 상태, 삭제 후 예약 정리 |
| 회원·자격 | 회원 검색·상세, 일반 progression, baseline, hold, 특수 클래스 승인 |
| 쿠폰·가족 | 신규·기존 쿠폰 등록, 가족 그룹과 공유 권한 관리 |
| 분석·감사 | 월간 기승 현황, 공동 1위, 예약·쿠폰·설정 감사 이력과 CSV |

Desktop에서는 고정 sidebar와 작업 본문을 권장한다. Mobile Web에서는 접히는 메뉴와 업무별 세로 목록을 사용한다.

예약 승인·반려·입금 확인·취소·복구는 하나의 예약 운영 workspace에서 상태별 queue, 상세 panel과 contextual action으로 통합할 수 있다. 각각을 독립 페이지로 만들 필요는 없다.

## 8. 상태 표현 원칙

### 예약 상태

| 내부 상태 | 사용자 표현 | 핵심 의미 |
|---|---|---|
| `pending_admin_approval` | 관리자 승인대기 | 정원과 쿠폰 1회를 임시 점유 |
| `pending_payment` | 입금 확인 대기 | 정원을 점유하며 입금 확인 대기 |
| `payment_expired` | 입금 기한 만료 | 정원 반환, 관리자 복구 가능성 안내 |
| `approval_expired` | 승인 기한 만료 | 승인되지 않아 정원과 쿠폰 점유 반환 |
| `confirmed` | 예약 확정 | 실제 수업 예정 |
| `completed` | 수업 완료 | 쿠폰 실제 차감과 기승 실적 반영 |
| `rejected` | 예약 반려 | 반려 사유 표시 |
| `cancelled` | 예약 취소 | 최종 쿠폰 처리 결과 표시 |
| `no_show` | 노쇼 | 관리자 처리 결과 확인 안내 |

승인대기 경고인 정상·확인 필요·긴급은 예약 상태와 별도 신호로 표현한다.

### 쿠폰과 결제

- 쿠폰은 신청 시 차감이 아니라 임시 점유되고 수업 완료 시 실제 차감된다.
- 쿠폰이 없으면 `pending_payment`가 되며 구체적인 마감은 제품 정책과 API 응답을 따른다.
- 프로토타입의 30분 입금 마감, 신용카드 결제, 가격 표시는 제거한다.
- 정확한 입금 계좌·금액 표시는 현재 API에서 확인되지 않으므로 디자인에 고정하지 않는다.

### 변경·취소·만료

- 전날 21:00은 신규 예약 마감이 아니라 예약 변경 정책의 경계다.
- 취소 결과는 시각, 책임 주체, 쿠폰 유형에 따라 달라지므로 고정 문구 대신 서버 preview를 사용한다.
- 마장 책임, 회원 책임, 운영 예외를 관리자에게는 명확히 보여주되 회원에게 내부 코드를 노출하지 않는다.
- 만료 상태에는 원인과 복구 또는 문의 행동을 함께 제공한다.
- 상태명만으로 행동 가능 여부를 추론하지 않고 API가 제공하는 허용 여부와 차단 사유를 사용한다.

## 9. 화면 상태

- **Loading**: 전체 페이지를 비우지 않고 제목·선택 조건을 유지한 채 skeleton 또는 inline progress 표시
- **Empty**: “0건”의 의미와 다음 행동 제공
- **Error**: 사용자 입력을 유지하고 원인별 메시지와 다시 시도 제공
- **Closed**: 예약 마감, 운영 마감, 정기 휴일, 개별 휴강을 회원 언어로 구분
- **Forbidden**: 권한 부족을 오류나 빈 목록으로 숨기지 않고 안전한 이동 경로 제공
- **Schedule update**: “일정 변경 사항을 반영하고 있습니다. 잠시 후 다시 시도해 주세요.”처럼 자연스럽게 안내
- **Conflict**: 선택 중 정원이나 상태가 바뀐 경우 최신 상태를 다시 불러오도록 안내
- **Partial result**: 일괄 출석처럼 일부 성공이 가능한 작업은 항목별 성공·실패를 유지

## 10. Responsive 원칙

- 320px부터 핵심 조작과 상태 확인 가능
- 본문 기본 크기 16px 이상, 터치 대상 44px 이상
- 회원 Web은 mobile-first, Desktop에서 정보 밀도를 확장
- 관리자 Web은 Desktop 우선의 밀도 높은 화면이지만 Mobile에서 축소된 표를 강요하지 않음
- 주간 캘린더는 Desktop에서 7일 시간표, 좁은 화면에서는 날짜별 agenda로 전환
- 표는 Mobile에서 핵심 필드 카드 또는 disclosure row로 전환
- 주요 실행 버튼은 긴 화면에서도 접근 가능하되 콘텐츠를 가리지 않음
- Mobile 앱은 로그인·예약·내 예약·쿠폰 회원 흐름만 MVP 4 후보로 구분
- MVP 4 모바일 시안을 현재 제공 중인 완성 기능처럼 표현하지 않음

## 11. 기존 HTML 처리

### 유지

- 기존 로고 시각 자산
- Burgundy 중심 브랜드
- 차분한 Off White 배경과 선 중심 구획
- 예약 요약, 상태 배지, 진행 결과, timeline의 정보 표현
- 날짜·시간 선택의 명확한 selected 상태
- skip link, focus ring, reduced-motion
- mobile bottom navigation 개념
- loading·empty·error·closed를 독립 상태로 설계한 접근

### 폐기 또는 재설계

- 고정된 7단계 wizard
- 존재하지 않는 체험 승마·가격·프로그램 시간
- 신용카드와 결제수단 선택
- 30분 입금 기한
- 예약 변경과 취소를 모두 전날 21:00으로 설명하는 문구
- 다섯 개뿐인 예약 상태
- 실제 데이터와 연결되지 않은 예약번호와 timeline
- 회원 예약만 존재하고 관리자 운영 화면이 없는 정보 구조
- 모바일 앱이 이미 제공되는 것처럼 보이는 구성

## 12. OpenDesign 화면 Inventory

이 Inventory는 **21개의 독립 route 또는 page를 반드시 만들어야 한다는 뜻이 아니다.**

현재 Horse의 전체 기능과 상태가 디자인에서 빠지지 않도록 하는 **design coverage 목록**이다.

같은 업무 맥락에 속한 기능은 다음 방식으로 통합할 수 있다.

- 하나의 workspace
- 상태별 tab
- list와 detail panel
- drawer
- dialog
- contextual action
- responsive disclosure

예를 들어 예약 승인, 반려, 입금 확인, 취소와 복구는 각각 별도 페이지가 아니라 하나의 예약 운영 workspace 안에서 처리할 수 있다.

### 공통 Coverage

1. 로그인
2. 회원가입
3. 권한 없음·세션 만료
4. 공통 responsive navigation과 계정 메뉴

### 회원 Coverage

5. 회원 홈
6. 수업 찾기·날짜·클래스·TimeSlot 선택
7. 예약 확인·신청 결과
8. 내 예약 목록·상세
9. 예약 변경
10. 예약 취소 preview·확인
11. 쿠폰과 사용 이력

### 관리자 Coverage

12. 관리자 운영 홈
13. 예약 운영 workspace
14. 출석·노쇼 workspace
15. 주간 운영 캘린더
16. 일정·휴무·개별 휴강 workspace
17. 정규 시간표·정기 휴일·동기화 workspace
18. 회원·자격·progression workspace
19. 쿠폰 등록·가족 그룹 workspace
20. 월간 기승 통계
21. 감사 이력·내보내기

MVP 4 모바일 시안은 공통 인증과 회원 Coverage의 핵심 흐름만 별도 플랫폼 변형으로 설계한다.

## 13. 디자인 우선순위

### 1차: 핵심 거래와 운영

- 공통 navigation·상태·form·dialog 디자인 시스템
- 로그인·회원가입
- 회원 수업 찾기·예약·내 예약·변경·취소
- 관리자 운영 홈·예약 승인·입금·취소·출석

### 2차: 일정과 회원 운영

## 14. 미확정 항목

- 최종 브랜드 표기 조합과 로고 원본 자산 규격
